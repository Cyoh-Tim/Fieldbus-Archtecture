## 0. 이 문서 읽는 법 + 선행 지식

### 0.1 읽는 순서

| 목적 | 읽을 절 |
|------|---------|
| "SLMP가 뭔지" 감만 잡기 | 1, 3 |
| 설정 파일(config)만 채우면 됨 | 2, 4, 9.3~9.4, 11 |
| 스택을 직접 구현 | 0 → 5 → 6 → 7 → 8 → 부록 A/B |
| 이 저장소 유지보수 | 9, 10, 부록 D (사양과의 차이) |

표기 규칙:

- `0x1234` 또는 `1234h` 는 16진수(hex). Mitsubishi 매뉴얼은 `1234H` 처럼 뒤에 H 를 붙인다.
- hex 덤프 `50 00 00 FF` 는 **네트워크로 실제 나가는 순서대로** 쓴 바이트열이다.
- **[검증]** 표시가 붙은 hex 예제는 이 저장소 스택을 빌드해 실제로 인코딩/디코딩한
  결과를 그대로 옮긴 것이다(10.6 절의 하네스).
- **[사양서 확인 필요]** 는 필자가 공식 사양서 원문으로 대조하지 못했거나, 기종별로
  달라서 단정할 수 없는 내용이다. 구현 전에 반드시 해당 사양서를 확인할 것.

### 0.2 비트, 바이트, 워드

| 단위 | 크기 | 비유 |
|------|------|------|
| 비트(bit) | 0 또는 1 | 전등 스위치 하나 |
| 바이트(byte) | 8비트, 0~255 | 스위치 8개짜리 패널 |
| 워드(word) | **16비트**, 0~65535 | 스위치 16개짜리 패널. PLC 세계의 기본 칸 |
| 더블워드(double word, DWORD) | 32비트 = 워드 2개 | |

주의: PC 프로그래밍(x86)에서 "word"가 문맥마다 다르게 쓰이지만, **PLC 세계에서 워드는
거의 항상 16비트**다.

### 0.3 16진수(hex)

16진수 한 자리는 4비트(니블, nibble)를 표현한다. 두 자리 = 1바이트.

```
0x0401  = 0000 0100 0000 0001 (2진)
          └─ 04 ─┘ └─ 01 ─┘   → 상위 바이트 0x04, 하위 바이트 0x01
```

SLMP 비트 단위 데이터는 **니블(4비트) 하나에 비트 디바이스 1점**을 담기 때문에
(5.7 절) 니블 개념이 실제로 중요하다.

### 0.4 엔디안(endianness) — SLMP 는 리틀엔디안

여러 바이트로 된 숫자를 네트워크에 보낼 때 "어느 바이트를 먼저 보내나"의 약속이다.

| 방식 | 0x1234 를 보내는 순서 | 쓰는 곳 |
|------|------------------------|---------|
| 빅엔디안(big-endian, BE) | `12 34` (큰 자리 먼저) | Modbus, TCP/IP 헤더, PROFINET |
| 리틀엔디안(little-endian, LE) | `34 12` (작은 자리 먼저) | **SLMP Binary**, x86/ARM CPU 메모리 |

**SLMP Binary 코드의 모든 다바이트 수치 필드는 리틀엔디안**이다. Modbus 를 먼저 배운
사람이 가장 많이 틀리는 지점이다. 예외처럼 보이는 것이 하나 있는데, 서브헤더(subheader)
`5000h` 는 바이트열 `50 00` 로 나간다(5.2 절). 이것은 "수치 0x5000 을 BE 로 보낸다"라기보다
**고정 바이트열 `50 00`** 이라고 외우는 편이 안전하다. (이 저장소는 이를 LE 수치
`0x0050` 으로 정의해 `wr_le16` 로 써서 같은 바이트 `50 00` 을 만든다 —
[`slmp_types.h:13-14`](../../stacks/slmp/include/slmp_types.h).)

3바이트 필드도 있다: 선두 디바이스 번호는 **3바이트 LE** 다. 100000(=0x0186A0) →
`A0 86 01`.

### 0.5 TCP vs UDP

| | TCP | UDP |
|---|-----|-----|
| 비유 | 전화 통화 (연결 후 대화, 순서·도착 보장) | 엽서 (보내면 끝, 분실·순서 뒤바뀜 가능) |
| 메시지 경계 | **없음** — 바이트 스트림. 수신 측이 길이 필드로 잘라야 함 | 데이터그램 1개 = 메시지 1개 |
| 재전송 | 커널이 자동 | 애플리케이션이 알아서 |
| SLMP | 지원 | 지원 |
| 이 저장소 | **TCP 만 구현** | 미구현 |

TCP 에서 "메시지 경계가 없다"는 말은, `recv()` 한 번에 프레임 반쪽이 올 수도, 프레임
두 개가 붙어서 올 수도 있다는 뜻이다. 그래서 SLMP 수신기는 항상 **"헤더 9바이트를 먼저
읽고 → 그 안의 길이 필드만큼 더 읽는다"** 는 방식으로 프레임을 잘라야 한다(6.3 절).

### 0.6 클라이언트/서버

- **클라이언트**: 요청(request)을 먼저 보내는 쪽.
- **서버**: 요청을 받아 응답(response)하는 쪽.

SLMP 에서는 **PLC 가 서버**, PC·HMI·센서·게이트웨이가 **클라이언트**인 것이 기본이다.
Mitsubishi 매뉴얼은 클라이언트를 "외부 기기(external device)" 또는 "상대 기기",
서버를 "SLMP 대응 기기"라고 부른다.

## 1. 왜 이 프로토콜이 존재하나

### 1.1 PLC 란

PLC(Programmable Logic Controller)는 공장 설비를 제어하는 산업용 컴퓨터다. 센서 입력을
읽고, 사다리 논리(ladder logic) 같은 프로그램을 수 ms 주기로 반복 실행해, 모터·밸브 출력을
낸다. PLC 내부 상태는 모두 **디바이스(device)** 라는 이름 붙은 메모리 칸에 들어 있다
(`D100` 에 온도, `M10` 에 "시작 버튼 눌림" 등, 4장).

Mitsubishi Electric(미쓰비시 전기)의 PLC 브랜드가 **MELSEC** 이고 주요 라인업은:

| 시리즈 | 위치 | 비고 |
|--------|------|------|
| MELSEC iQ-R | 최상위 모듈형 | 내장 이더넷, SLMP 지원 |
| MELSEC-Q (QnU, QnUDE 등) | 이전 세대 모듈형, 여전히 현장 다수 | QnUDE 계열 내장 이더넷, QJ71E71 이더넷 모듈 |
| MELSEC-L | 중형 | |
| MELSEC iQ-F (FX5) | 소형 | 내장 이더넷 SLMP 지원 |
| FX3 이하 | 구형 소형 | 주로 1E 프레임(A 호환) 계열 [사양서 확인 필요] |

### 1.2 MC 프로토콜 → SLMP

외부 PC 가 PLC 메모리를 읽고 쓰려면 약속된 메시지 형식이 필요하다. Mitsubishi 는
오래전부터 이를 **MC 프로토콜(MELSEC Communication Protocol)** 이라 불렀다. MC 프로토콜에는
세대별로 여러 "프레임"이 있다.

| 프레임 | 다른 이름 | 특징 |
|--------|-----------|------|
| 1E | A 호환 1E | 구형 A 시리즈용. 헤더가 짧고 디바이스 코드 체계가 다름 |
| **3E** | **QnA 호환 3E** | Q 시리즈 이후의 표준. 네트워크 번호·국번·모듈 I/O 로 라우팅 |
| 4E | QnA 호환 4E | 3E + **시리얼 번호**(요청/응답 짝 맞추기) |

2010년 전후로 Mitsubishi 와 CC-Link 협회(CLPA)는 이 메시지 체계를 이더넷·CC-Link IE 계열에서
공통으로 쓰는 **SLMP(Seamless Message Protocol)** 로 이름 붙이고 문서화했다. 실무 관점에서:

- **SLMP 3E/4E Binary 프레임 = MC 프로토콜 QnA 호환 3E/4E Binary 프레임과 바이트 수준에서 같다.**
  그래서 "MC 프로토콜 3E 라이브러리"로 SLMP 대응 PLC 와 통신할 수 있고, 반대도 된다.
- SLMP 는 "Seamless" 라는 이름처럼 이더넷 ↔ CC-Link IE 네트워크를 넘어 다른 국(station)까지
  메시지를 중계할 수 있도록 헤더에 **네트워크 번호/국번** 을 둔다(2장, 5장).
- iQ-R 에서는 디바이스 번호를 4바이트로 확장한 서브커맨드(`0002`/`0003`)가 추가되었다.
  이 저장소는 Q 호환 서브커맨드(`0000`/`0001`)만 쓴다.

타사(KEYENCE KV, OMRON 의 SLMP 라이브러리, 각종 HMI/게이트웨이)도 3E Binary 를 지원하는
경우가 많아, 사실상 "Mitsubishi 호환 PLC 이더넷 공용어" 역할을 한다.

### 1.3 CC-Link IE 계열과의 관계

CC-Link / CC-Link IE Field / CC-Link IE TSN 은 CLPA 가 관리하는 **필드버스**(주기적으로
I/O 를 교환하는 산업 네트워크)다. SLMP 는 이들 네트워크의 **비주기(transient) 메시지** 계층으로
정의되어 있고, CC-Link IE Field Network Basic 은 표준 이더넷 위에서 SLMP 기반으로
동작하는 것으로 알려져 있다 [세부 포트/프레임은 사양서 확인 필요].

비유하면:

- CC-Link IE 의 주기 통신 = **매 순간 자동 동기화되는 공유 칠판** (PROFINET RT, EtherNet/IP Class 1 과 비슷)
- SLMP = **필요할 때 보내는 편지** ("D100 부터 2칸 읽어 주세요")

이 저장소는 CC-Link 어댑터를 스텁으로만 두고(사양 미확정, [CLAUDE.md](../../CLAUDE.md)),
SLMP 는 **표준 TCP/IP 위의 3E Binary 요청/응답** 만 다룬다.

### 1.4 "센서가 클라이언트로 PLC 메모리에 쓴다" 구조

Modbus TCP 에서는 흔히 센서가 서버가 되어 PLC 가 센서를 읽어 간다. SLMP 현장에서는 반대가
흔하다. **PLC 는 서버(디바이스 메모리를 가진 쪽)**이고, 센서·바코드 리더·비전 장비가
클라이언트로 접속해 **PLC 의 특정 디바이스(D100 등)에 직접 값을 써 넣는다.**

```
[바코드 리더]  --TCP 접속-->  [MELSEC PLC :포트]
   "D100~D115 에 'ABC123...' 써 주세요"  (batch write)
   <-- "완료(end code 0000)"
   "M10 (트리거 비트) 읽어 주세요"         (batch read)
   <-- "M10 = ON"
```

PLC 프로그램(래더)은 D100 에 새 바코드가 들어왔는지 보고 동작한다. PLC 쪽 프로그래머는
"D100 부터 32 워드, ASCII" 같은 **주소표(통신 가이드)** 만 정해 주면 된다. 이 저장소의 SLMP
어댑터 기본 역할도 정확히 이 **클라이언트** 다
([`docs/slmp_stack.md`](../slmp_stack.md) 2장,
[`slmp_types.h:51-54`](../../stacks/slmp/include/slmp_types.h)).

## 2. 용어 사전

| 용어 (영/일) | 뜻 | 3E 프레임 위치/예 |
|--------------|----|-------------------|
| 디바이스 (device / デバイス) | PLC 메모리 영역의 종류. D, M, X, Y ... | `D100` 의 `D` |
| 디바이스 번호 (device number) | 영역 안의 칸 번호. 디바이스에 따라 10진 또는 16진 표기 | `D100` 의 `100`, `X1A` 의 `1A`(16진) |
| 선두 디바이스 (head device / 先頭デバイス) | 연속 읽기/쓰기의 시작 번호 | 요청 오프셋 15~17 (3바이트 LE) |
| 디바이스 코드 (device code) | 디바이스 종류를 나타내는 1바이트 코드 (Binary) | D=`A8h`, M=`90h` (부록 C) |
| 워드 디바이스 (word device) | 칸 하나가 16비트인 디바이스 | D, W, R, ZR, SD, TN, CN |
| 비트 디바이스 (bit device) | 칸 하나가 1비트인 디바이스 | X, Y, M, L, B, SM, TS, CS |
| 점수 (number of points / 点数) | 몇 칸을 읽고/쓸지. 워드 단위면 워드 수, 비트 단위면 비트 수 | 요청 오프셋 19~20 |
| 워드 단위 / 비트 단위 접근 | 비트 디바이스도 16개씩 묶어 워드로 접근 가능 | 서브커맨드 `0000`(워드) / `0001`(비트) |
| 서브헤더 (subheader) | 프레임 종류 식별자 | 요청 `50 00`, 응답 `D0 00` |
| 네트워크 번호 (network No.) | 접근 대상이 속한 네트워크. 자기(직결) 네트워크면 `00` | 오프셋 2 |
| 국번 / PC 번호 (PC No. / station No.) | 네트워크 내 대상 국. 직결 CPU 는 `FFh` | 오프셋 3 |
| 요구처 유닛 I/O 번호 (request destination module I/O No.) | 대상 국 안의 어느 모듈(CPU)인가. 자기 CPU = `03FFh` | 오프셋 4~5 (LE: `FF 03`) |
| 요구처 멀티드롭 국번 (request destination multidrop station No.) | 멀티드롭(시리얼 다중 접속) 대상 국. 보통 `00` | 오프셋 6 |
| 요구 데이터 길이 (request data length) | 이 필드 **뒤부터** 프레임 끝까지의 바이트 수 | 오프셋 7~8 |
| 감시 타이머 / 모니터링 타이머 (monitoring timer / 監視タイマ) | PLC 가 처리를 기다리는 최대 시간. **250 ms 단위**, `0` = 무한 대기 | 오프셋 9~10 |
| 커맨드 (command) | 무엇을 할지 | `0401h` 일괄 읽기, `1401h` 일괄 쓰기 |
| 서브커맨드 (subcommand) | 커맨드의 세부 모드 | `0000h` 워드, `0001h` 비트 |
| 응답 데이터 길이 (response data length) | 응답에서 이 필드 뒤부터 끝까지 바이트 수 | 응답 오프셋 7~8 |
| 종료 코드 / 엔드 코드 (end code / 終了コード) | 처리 결과. `0000h` 정상, 그 외 이상 | 응답 오프셋 9~10 |
| 에러 정보 (error information) | 이상 종료 시 엔드 코드 뒤에 붙는 진단 정보 | 5.9 절 |
| 시리얼 번호 (serial No.) | 4E 프레임에서 요청/응답 짝 맞추기용 | 3E 에는 없음 |
| 교신 데이터 코드 (communication data code) | Binary 또는 ASCII. PLC 설정과 반드시 일치 | PLC 파라미터 |
| 자국 / 타국 (own station / other station) | 직접 연결된 PLC / 네트워크 너머의 PLC | 네트워크 번호·국번으로 지정 |
| 일괄 (batch / 一括) | 연속 구간을 한 번에 | `0401`, `1401` |
| 랜덤 (random / ランダム) | 흩어진 여러 디바이스를 한 번에 | `0403`, `1402` (이 저장소 미구현) |
| 블록 (block) | 연속 구간 여러 개를 한 번에 | `0406`, `1406` (미구현) |

## 4. 데이터 모델 — PLC 디바이스 메모리

### 4.1 디바이스는 "이름 붙은 배열"이다

PLC 메모리를 C 로 비유하면 디바이스마다 전역 배열이 있는 것과 같다.

```c
/* 비유일 뿐, 실제 PLC 내부 구현이 이렇다는 뜻은 아님 */
bool     X[...];   /* 입력 (외부 스위치/센서 → PLC) */
bool     Y[...];   /* 출력 (PLC → 램프/모터) */
bool     M[...];   /* 내부 릴레이 (프로그램 내부 플래그) */
uint16_t D[...];   /* 데이터 레지스터 (숫자 저장) */
uint16_t W[...];   /* 링크 레지스터 (네트워크 공유 영역) */
```

`D100` 은 `D[100]`, `M10` 은 `M[10]` 이다. 각 배열 크기(디바이스 점수)는 PLC 기종과
파라미터 설정에 따라 다르다(예: D 는 수천~수만 점). 범위 밖을 접근하면 PLC 가 에러
엔드 코드로 응답한다.

### 4.2 주요 디바이스

| 기호 | 이름 (영/일) | 종류 | 번호 표기 | 흔한 용도 |
|------|--------------|------|-----------|-----------|
| X | Input / 入力 | 비트 | **16진** (Q/iQ-R) | 외부 입력 접점 |
| Y | Output / 出力 | 비트 | **16진** (Q/iQ-R) | 외부 출력 |
| M | Internal relay / 内部リレー | 비트 | 10진 | 프로그램 내부 플래그, 트리거 |
| L | Latch relay / ラッチリレー | 비트 | 10진 | 정전 유지 플래그 |
| F | Annunciator / アナンシェータ | 비트 | 10진 | 고장 표시 |
| V | Edge relay / エッジリレー | 비트 | 10진 | |
| B | Link relay / リンクリレー | 비트 | **16진** | 네트워크 공유 비트 |
| S | Step relay | 비트 | 10진 | SFC |
| SM | Special relay / 特殊リレー | 비트 | 10진 | 시스템 상태 (예: 항상 ON 등) |
| SB | Link special relay | 비트 | **16진** | 네트워크 상태 |
| DX / DY | Direct input/output | 비트 | **16진** | 리프레시 없이 직접 I/O |
| TS / TC / TN | Timer contact / coil / current value | 비트/비트/워드 | 10진 | 타이머 |
| SS / SC / SN | Retentive timer contact / coil / current value | 비트/비트/워드 | 10진 | 적산 타이머 (매뉴얼에 따라 STS/STC/STN 표기) |
| CS / CC / CN | Counter contact / coil / current value | 비트/비트/워드 | 10진 | 카운터 |
| D | Data register / データレジスタ | 워드 | 10진 | **가장 흔한 데이터 교환 영역** |
| W | Link register / リンクレジスタ | 워드 | **16진** | 네트워크 공유 워드 |
| SD | Special register / 特殊レジスタ | 워드 | 10진 | 시스템 정보 (에러 코드 등) |
| SW | Link special register | 워드 | **16진** | 네트워크 상태 |
| R | File register / ファイルレジスタ | 워드 | 10진 | 대용량 저장 (블록 전환식) |
| ZR | File register (serial number access) | 워드 | 10진 (iQ-R) / 16진 (Q 계열 MC 매뉴얼 표기라는 자료가 있음) **[사양서 확인 필요]** | 연번 접근 파일 레지스터 |
| Z | Index register / インデックスレジスタ | 워드 | 10진 | 주소 수식 |

### 4.3 10진/16진 번호 체계 — 가장 흔한 실수

**X, Y, B, W, SB, SW, DX, DY 는 번호를 16진수로 읽는다.** (Q/iQ-R/L 기준)

| 가이드 표기 | 실제 번호(10진) | 3바이트 LE 인코딩 |
|-------------|-----------------|--------------------|
| `D100` | 100 | `64 00 00` |
| `X1A` | 0x1A = 26 | `1A 00 00` |
| `X100` | 0x100 = 256 (10진 100 아님!) | `00 01 00` |
| `W1F` | 0x1F = 31 | `1F 00 00` |
| `ZR100000` (10진으로 해석 시) | 100000 | `A0 86 01` |

그리고 **FX5(iQ-F)의 X/Y 는 8진수(octal) 표기**다(GX Works3 에서 `X17` 다음이 `X20`).
SLMP 에서 FX5 의 X/Y 번호를 어떻게 넣는지(8진 해석 값을 이진 수치로 넣는지)는 FX5 SLMP
매뉴얼의 디바이스 표로 확인해야 한다 **[사양서 확인 필요]**. 이 저장소는 X/Y 를 무조건
16진으로 파싱하므로(9.5 절) FX5 를 대상으로 할 때는 문자열 대신 **숫자 번호를 직접**
주는 편이 안전하다.

프레임 위에는 항상 **이진 수치**가 올라간다. "16진 표기"는 사람이 읽는 이름(`X1A`)에서
번호를 해석하는 규칙일 뿐, 프레임에 문자 `'1' 'A'` 가 들어가는 것이 아니다(그건 ASCII
프레임의 이야기, 5.11 절).

### 4.4 디바이스 코드 (Binary, 1바이트)

Q 호환 서브커맨드(`0000`/`0001`)에서 디바이스 종류는 1바이트 코드다. 아래 값은 이 저장소
표([`slmp_types.h:63-90`](../../stacks/slmp/include/slmp_types.h),
[`slmp_stack.c:52-67`](../../stacks/slmp/src/slmp_stack.c))와 공개 오픈소스 구현
(pymcprotocol `DeviceConstants`)을 교차 확인한 값이며 모두 일치했다. 전체 표는 부록 C.

| 디바이스 | 코드 | 디바이스 | 코드 | 디바이스 | 코드 |
|----------|------|----------|------|----------|------|
| X | `9C` | D | `A8` | TS | `C1` |
| Y | `9D` | W | `B4` | TC | `C0` |
| M | `90` | R | `AF` | TN | `C2` |
| L | `92` | ZR | `B0` | CS | `C4` |
| F | `93` | SD | `A9` | CC | `C3` |
| V | `94` | SW | `B5` | CN | `C5` |
| B | `A0` | Z | `CC` | SS | `C7` |
| SM | `91` | DX | `A2` | SC | `C6` |
| SB | `A1` | DY | `A3` | SN | `C8` |
| S | `98` | | | | |

iQ-R 전용 디바이스(LTS/LTC/LTN, LSTS/LSTC/LSTN, LCS/LCC/LCN, LZ, RD 등)는 확장
서브커맨드(`0002`/`0003`)에서 **2바이트 디바이스 코드 + 4바이트 번호**를 쓴다
[세부 형식 사양서 확인 필요]. 이 저장소는 지원하지 않는다.

### 4.5 비트 단위 vs 워드 단위 접근

같은 비트 디바이스라도 두 가지로 접근할 수 있다.

```
M0 ~ M31 (비트 32개)

비트 단위 (서브커맨드 0001): "M0 부터 32점"   → 32개의 ON/OFF
워드 단위 (서브커맨드 0000): "M0 부터 2워드"  → 워드0 = M0..M15, 워드1 = M16..M31

워드0 비트 배치:  bit15 ............................ bit0
                  M15 M14 M13 ... M2  M1  M0
```

워드 단위로 읽은 1워드의 **bit0 이 선두 디바이스(M0)**, bit15 가 M15 다. 워드 단위에서
선두 번호는 여전히 **비트 디바이스 번호**(예: `M16` 이면 M16~M31)이다. 워드 단위 접근 시
선두 번호를 16의 배수로 해야 하는지는 기종/커맨드에 따라 제약이 있을 수 있다
**[사양서 확인 필요]**.

반대로 워드 디바이스(D 등)를 비트 단위로 접근하는 것은 일괄 읽기/쓰기에서 허용되지 않는
것이 일반적이다(PLC 가 에러 응답) **[사양서 확인 필요]**. D 레지스터 안의 특정 비트
(`D300.3`)가 필요하면 워드로 읽고 비트 마스크로 뽑는다(이 저장소의 `bit` 필드가 이 방식,
9.4 절).

### 4.6 32비트 정수 / float / 문자열 담는 법 (MELSEC 관례)

SLMP 는 **16비트 워드의 배열**만 운반한다. 더 큰 값은 워드 여러 개에 나눠 담으며,
MELSEC 의 관례는 다음과 같다(래더의 `DMOV`, `EMOV`, `$MOV` 명령이 만드는 배치).

**(1) 32비트 정수 / 단정밀도 float: 하위 워드가 앞 번호**

```
값 0x3FC00000 (float 1.5) 를 D200 에 저장
  D200 = 0x0000  (하위 16비트)
  D201 = 0x3FC0  (상위 16비트)

프레임 위 (각 워드 LE):  00 00 C0 3F      ← 전체로 보면 32비트 LE 와 같다 [검증]
```

즉 SLMP Binary 로 읽은 워드 데이터 4바이트를 그대로 x86 메모리에 memcpy 하면 float 이 된다.
(이 저장소 어댑터 어휘로는 `"endian": "CDAB"` 가 이 배치 — 9.4 절.)

**(2) 문자열: 워드마다 2문자, 앞 문자가 하위 바이트**

```
"ABCD" 를 D100 에 저장 ($MOV 관례)
  D100 = 0x4241  ('B'<<8 | 'A')
  D101 = 0x4443  ('D'<<8 | 'C')

프레임 위 (워드 LE): 41 42 43 44  = "ABCD" 가 그대로 순서대로 보인다 [검증]
```

GX Works 의 디바이스 모니터에서 D100 을 16진으로 보면 `4241` 로 보인다는 점에 주의.
(이 저장소 어댑터에서는 `"string_swap": true` 일 때 이 배치가 된다 — 9.4 절, 11.1 절.)

**(3) BCD**: 일부 구형 장비·표시기는 10진 자릿수를 니블에 담는 BCD 를 쓴다. `1234` →
`0x1234`. 필요하면 변환(`slmp_bcd_to_u32`, [`slmp_codec.c:266`](../../adapters/slmp/slmp_codec.c)).

**(4) 64비트 / double**: 워드 4개, 역시 하위 워드가 앞 번호가 MELSEC 관례다.

                                          └──────────────── len 이 세는 범위 (오프셋 9 ~ 끝) ───────────────┘

응답 (Response)
 오프셋: 0     2    3    4       6    7       9          11
       ┌─────┬────┬────┬───────┬────┬───────┬──────────┬──────────────────────────────┐
       │D0 00│net │ pc │ I/O   │ md │ len   │ end code │ 읽은 데이터 (정상) 또는        │
       │     │ (요청 값 에코)         │ 2B LE │ 2B LE    │ 에러 정보 9B (이상, 5.9 절)    │
       └─────┴────┴────┴───────┴────┴───────┴──────────┴──────────────────────────────┘
                                          └──────── len 이 세는 범위 (오프셋 9 ~ 끝) ────┘
```

핵심 규칙 세 가지:

1. **길이 필드(오프셋 7~8)는 "그 뒤"를 센다.** 요청에서는 감시 타이머부터, 응답에서는
   엔드 코드부터 끝까지. 그래서 전체 프레임 길이 = `9 + len`.
2. **모든 다바이트 수치는 리틀엔디안.** (서브헤더는 고정 바이트 `50 00` / `D0 00`.)
3. **3E 에는 요청/응답 짝을 맞출 ID 가 없다.** 순서로만 매칭한다(6.1 절).

### 5.7 예제 3 — 비트 일괄 읽기/쓰기와 **니블 패킹**

**사양의 비트 단위 데이터 형식 (Binary):** 1점 = 4비트(니블). 1바이트에 2점을 담으며,
**앞 디바이스가 상위 니블(bit4~7), 다음 디바이스가 하위 니블(bit0~3)**. ON = `1`, OFF = `0`.
점수가 홀수이면 마지막 바이트의 하위 니블은 `0` 으로 채운다. 따라서 데이터 바이트 수 =
`ceil(점수 / 2)`.

> 근거: Mitsubishi 매뉴얼의 비트 단위 설명(1점을 4비트로 표현)과, 독립적인 두 오픈소스
> 구현(pymcprotocol `batchread_bitunits`: 짝수 인덱스는 bit4, 홀수 인덱스는 bit0 /
> mc-protocol-3e `mc_3e.py`: `data[i//2] >> (4 if i%2==0 else 0)`)이 모두 이 형식이다.

```
M0..M3 = ON, OFF, ON, ON

  바이트 0:  [ M0=1 | M1=0 ]  → 0x10
  바이트 1:  [ M2=1 | M3=1 ]  → 0x11
```

**사양 준수 요청/응답 — M0 부터 4점 비트 일괄 읽기:**

```
요청 (21B): 50 00 00 FF FF 03 00 0C 00 10 00 01 04 01 00 00 00 00 90 04 00   [검증: 저장소 인코더와 동일]
응답 (13B): D0 00 00 FF FF 03 00 04 00 00 00 10 11                            [사양 기준으로 작성]
```

**사양 준수 요청 — M0 부터 4점 비트 일괄 쓰기 (1,0,1,1):**

```
50 00 00 FF FF 03 00 0E 00 10 00 01 14 01 00 00 00 00 90 04 00 10 11
                     └ len=14 = 12 + ceil(4/2)                    └ 데이터 2바이트
```

> **이 저장소와의 차이 (중요, 부록 D-1):** 이 저장소 스택은 비트 단위 데이터를 **1점 = 1바이트
> (`00`/`01`)** 로 인코딩·디코딩한다
> ([`slmp_stack.c:505-506`](../../stacks/slmp/src/slmp_stack.c) "1 byte/bit",
> [`:750-763`](../../stacks/slmp/src/slmp_stack.c), [`:900-906`](../../stacks/slmp/src/slmp_stack.c),
> [`:930`](../../stacks/slmp/src/slmp_stack.c)). 실측 [검증]:
>
> ```
> 저장소 비트 쓰기 M0..M3 (1,0,1,1): 50 00 00 FF FF 03 00 10 00 10 00 01 14 01 00 00 00 00 90 04 00 01 00 01 01
> 저장소 비트 읽기 응답            : D0 00 00 FF FF 03 00 06 00 00 00 01 00 01 01
> ```
>
> 저장소 클라이언트 ↔ 저장소 서버끼리는 서로 같은 규칙이라 테스트가 통과하지만, **실 PLC 와는
> 비트 단위 경로가 호환되지 않는다.** 예를 들어 1점 ON 쓰기를 저장소는 데이터 `01` 로 보내는데,
> 사양상 `01` 은 "상위 니블(해당 점) = 0 = OFF" 이다. 사양대로 니블 패킹된 요청(위 23바이트)을
> 저장소 서버에 넣으면 데이터 길이 부족으로 `-EBADMSG` 가 되어 **응답 없이 버려진다** [검증].
> 워드 단위 경로(서브커맨드 `0000`)는 사양과 일치한다.

### 5.9 엔드 코드와 에러 응답 형식

**정상**: 엔드 코드 `0000h`, 뒤에 데이터(읽기) 또는 없음(쓰기).

**이상**: 엔드 코드 ≠ 0. 사양상 이상 응답에는 엔드 코드 뒤에 **에러 정보 9바이트** 가 붙는다.
에러 정보는 "에러를 검출한 국/모듈" 과 "어떤 커맨드였는지" 를 알려 준다.

```
D0 00 | 00 FF FF 03 00 | 0B 00 | 56 C0 | 00 FF FF 03 00 01 04 00 00
서브헤더  에코             len=11   엔드   └────────── 에러 정보 ──────────┘
                                  C056h   net pc  I/O   md  cmd   subcmd
```

| 에러 정보 필드 | 크기 |
|----------------|------|
| 네트워크 번호 (응답국) | 1 |
| PC 번호 (응답국) | 1 |
| 요구처 유닛 I/O 번호 | 2 |
| 요구처 멀티드롭 국번 | 1 |
| 커맨드 | 2 |
| 서브커맨드 | 2 |

(위 필드 구성은 MC/SLMP 매뉴얼의 이상 응답 형식을 바탕으로 한 것이다. 각 값이 어느 국 기준인지
세부는 **[사양서 확인 필요]**.)

클라이언트 구현 시 권장: **응답 길이 필드를 믿고 프레임 끝까지 읽은 뒤**, 엔드 코드가 0 이
아니면 뒤의 바이트는 에러 정보로 로깅만 하고 데이터로 해석하지 않는다. 에러 정보가 없는 응답
(길이 2)도 방어적으로 허용한다.

> **이 저장소와의 차이 (부록 D-3):** 저장소 서버의 이상 응답은 **에러 정보 없이 엔드 코드만**
> 보낸다([`slmp_stack.c:836-858`](../../stacks/slmp/src/slmp_stack.c), 실측
> `D0 00 00 FF FF 03 00 02 00 56 C0` [검증]). 저장소 클라이언트는 엔드 코드만 보므로 실 PLC 의
> 11바이트 에러 응답도 문제없이 처리한다.

**대표 엔드 코드** (Q/L 호환 3E 에서 널리 인용되는 값. 의미 문구와 기종별 추가 코드는
**[사양서 확인 필요]**):

| 엔드 코드 | 대략적 의미 |
|-----------|-------------|
| `0000h` | 정상 완료 |
| `C050h` | 교신 데이터 코드가 ASCII 일 때 이진 변환할 수 없는 ASCII 데이터 수신 |
| `C051h`~`C054h` | 읽기/쓰기 점수가 허용 범위 밖 |
| `C056h` | 읽기/쓰기 요청이 최대 어드레스(디바이스 범위)를 초과 |
| `C058h` | ASCII→Binary 변환 후 요구 데이터 길이가 실제 데이터와 불일치 |
| `C059h` | 커맨드/서브커맨드 지정 오류, 또는 해당 CPU 가 지원하지 않는 커맨드 |
| `C05Bh` | CPU 가 지정 디바이스를 읽고/쓸 수 없음 |
| `C05Ch` | 요구 내용 오류 (예: 워드 디바이스를 비트 단위로 지정) |
| `C061h` | 요구 데이터 길이가 데이터 수와 불일치 |
| `C06Fh` | 교신 데이터 코드(Binary/ASCII) 설정 불일치로 알려짐 |
| `C0D8h`, `C200h`대 | 블록 수 초과 / 원격 패스워드 관련으로 알려짐 |
| `4000h`~`4FFFh` | CPU 모듈이 검출한 에러 (CPU 에러 코드 표 참조) |

> **이 저장소와의 차이 (부록 D-2):** 저장소는 미지원 커맨드/서브커맨드에 `C050h` 를
> 쓴다([`slmp_types.h:31`](../../stacks/slmp/include/slmp_types.h) 주석 "command /
> subcommand not supported"). 사양에서 이 의미는 `C059h` 이고 `C050h` 는 ASCII 변환 오류다.
> 또 알 수 없는 디바이스 코드와 범위 초과를 모두 `C056h` 로 응답한다
> ([`slmp_stack.c:884-887`](../../stacks/slmp/src/slmp_stack.c), [`:921-924`](../../stacks/slmp/src/slmp_stack.c)).
> 실 PLC 는 디바이스 코드 오류에 다른 코드(`C05Bh`/`C05Ch` 등)를 줄 수 있다.
> CTT 시나리오(`reject_non_3e.yaml` 의 `end_code: 0xC050`)가 이 값을 고정하고 있으므로,
> 바꾸려면 시나리오도 함께 바꿔야 한다.

### 5.10 3E vs 4E

| | 3E | 4E |
|---|----|----|
| 요청 서브헤더 | `50 00` | `54 00` + **시리얼 번호 2B** + `00 00` |
| 응답 서브헤더 | `D0 00` | `D4 00` + 시리얼 번호(에코) + `00 00` |
| 이후 | 동일 (네트워크 번호부터) | 동일 |
| 요청/응답 매칭 | 순서만 | 시리얼 번호로 매칭 → 파이프라인 가능 |

4E 요청 예 (시리얼 `1234h`, 나머지는 예제 1과 같음 — 사양 기준 작성, 저장소 미구현):

```
54 00 34 12 00 00 | 00 FF FF 03 00 0C 00 10 00 01 04 00 00 64 00 00 A8 02 00
```

4E 는 UDP 처럼 응답 순서/유실이 불확실한 환경이나, 여러 요청을 동시에 띄우는(pipelining)
클라이언트에 유리하다. 시리얼 번호 필드의 바이트 순서는 사양서 확인 권장(값을 그대로 에코하므로
클라이언트 입장에선 상관없다).

이 저장소: `SLMP_FRAME_4E_BINARY` 는 enum 예약만 있고
([`slmp_types.h:56-60`](../../stacks/slmp/include/slmp_types.h)), `slmp_stack_create` 가 3E Binary
외에는 거절한다([`slmp_stack.c:239-242`](../../stacks/slmp/src/slmp_stack.c)).

### 5.11 Binary vs ASCII

같은 요청을 ASCII 코드로 보내면 **모든 필드를 16진 문자로, 큰 자리부터(빅엔디안 텍스트)** 쓴다.
디바이스 코드는 2문자(`D*`, `M*`, `X*` 등), 디바이스 번호는 6자리(디바이스에 따라 10진/16진 문자).

예제 1 (D100 2워드 읽기)을 ASCII 3E 로 쓰면 (사양 기준 작성, 저장소 미구현):

```
"5000" "00" "FF" "03FF" "00" "0018" "0010" "0401" "0000" "D*" "000100" "0002"
 서브헤더 net  pc   I/O   md   길이   타이머  cmd    sub    코드  번호     점수
```

→ 전송 문자열 `500000FF03FF000018001004010000D*0001000002` (42바이트).
길이 `0018h` = 24 = 타이머 4 + cmd 4 + sub 4 + 코드 2 + 번호 6 + 점수 4 (문자 수).

| | Binary | ASCII |
|---|--------|-------|
| 크기 | 작음 (예제 1: 21B) | 약 2배 (42B) |
| 사람이 읽기 | 어려움 | 쉬움 (텔넷으로도 테스트 가능) |
| 바이트 순서 | LE | 텍스트라 BE 순서 |
| PLC 설정 | "교신 데이터 코드 = Binary" | "= ASCII" |
| 이 저장소 | **구현** | enum 예약만 ([`slmp_types.h:58`](../../stacks/slmp/include/slmp_types.h)) |

PLC 의 교신 데이터 코드 설정과 클라이언트 프레임 종류가 다르면 PLC 는 에러로 응답하거나 응답하지
않을 수 있다(7.5 절).

### 5.12 (참고) 이 저장소 범위 밖 커맨드의 요청 본문 모양

직접 구현을 확장할 때를 위한 개요다. **필드 순서/크기는 반드시 사양서로 확인할 것.**

| 커맨드 | 커맨드/서브 뒤 본문 (Q 호환 서브커맨드 기준, 개요) |
|--------|-----------------------------------------------------|
| `0403` 랜덤 읽기 | 워드 점수(1B), 더블워드 점수(1B), 이어서 각 디바이스 [번호 3B + 코드 1B] 나열 |
| `1402`/`0000` 랜덤 쓰기(워드) | 워드 점수(1B), 더블워드 점수(1B), [디바이스 4B + 값 2B]..., [디바이스 4B + 값 4B]... |
| `1402`/`0001` 랜덤 쓰기(비트) | 비트 점수(1B), [디바이스 4B + ON/OFF 1B]... |
| `0406` 블록 읽기 | 워드 블록 수(1B), 비트 블록 수(1B), [디바이스 4B + 점수 2B]... |
| `1001` 원격 RUN | 모드/클리어 모드 등 옵션 필드 |
| `0101` 형명 읽기 | 본문 없음. 응답: 형명 문자열 16B + 형명 코드 2B |

## 6. 동작과 상태

### 6.1 클라이언트의 요청/응답 매칭

3E 프레임에는 트랜잭션 ID 가 없다. 그러므로 한 TCP 연결에서:

1. 요청 1개를 보낸다.
2. 그 응답 1개를 **완전히** 받는다(헤더 9바이트 + 길이만큼).
3. 그 다음에야 다음 요청을 보낸다.

비유: 번호표 없는 창구. 한 사람이 창구에 서 있는 동안 다음 사람은 기다린다. 두 사람이 동시에
서류를 내밀면 창구 직원이 돌려주는 서류가 누구 것인지 알 수 없다.

응답 검증 권장 항목:

| 검사 | 이유 |
|------|------|
| 서브헤더 = `D0 00` | 프레임 종류/동기 확인 |
| 네트워크/PC/I/O/멀티드롭 에코 = 보낸 값 | 다른 요청의 응답이 섞였는지 약하게나마 감지 |
| 응답 길이 ≥ 2 | 엔드 코드가 반드시 있어야 함 |
| 읽기 정상 응답의 데이터 길이 = 기대값 | 워드: `2n`, 비트: `ceil(n/2)` |

이 저장소 클라이언트 `client_transact`
([`slmp_stack.c:644-680`](../../stacks/slmp/src/slmp_stack.c))는 요청 전송 → 헤더 9바이트 수신 →
서브헤더 확인 → 길이만큼 수신 순으로 동작한다. 에코 필드는 검사하지 않는다.

여러 요청을 동시에 처리하고 싶다면 선택지는 두 가지다: (a) TCP 연결을 여러 개 연다(PLC 의 연결 수
제한 주의), (b) 4E 프레임의 시리얼 번호로 매칭한다.

### 6.2 TCP 와 UDP 의 차이

| 항목 | TCP | UDP |
|------|-----|-----|
| 연결 | 먼저 `connect()`. PLC 쪽에 해당 포트를 "SLMP/MC, TCP" 로 열어 둬야 함 | 연결 없음. PLC 쪽 포트를 "UDP" 로 열어 둠 |
| 프레임 경계 | 직접 잘라야 함 (6.3) | 데이터그램 = 프레임 1개 |
| 유실 | 없음 (끊김은 감지) | 있음 → 타임아웃 후 재전송 필요 |
| 중복/지연 응답 | 거의 없음 | 가능 → 4E 시리얼 번호 권장 |
| 여러 클라이언트 | 연결 수만큼 | 같은 포트를 여러 송신자가 공유 가능 |
| 이 저장소 | 구현 (`tcp_connect_client` [`:951`](../../stacks/slmp/src/slmp_stack.c), `tcp_listen_server` [`:991`](../../stacks/slmp/src/slmp_stack.c)) | 미구현 |

UDP 로 **쓰기** 요청을 재전송할 때는 "첫 요청이 실제로는 처리됐는데 응답만 유실된" 경우 쓰기가 두 번
일어날 수 있다. 같은 값을 쓰는 일괄 쓰기는 두 번 해도 결과가 같지만(멱등), 원격 RUN/STOP 같은
커맨드는 주의해야 한다.

### 6.3 TCP 수신 프레이밍 알고리즘

```
버퍼 buf, 길이 n 을 연결마다 유지

on_readable:
    n += recv(fd, buf+n, CAP-n)
    if recv == 0: 연결 종료 처리
    while n >= 9:
        len = buf[7] | buf[8] << 8          # LE
        total = 9 + len
        if total > CAP: 프로토콜 위반 → 연결 끊기
        if n < total: break                  # 나머지가 아직 안 옴
        handle_frame(buf, total)
        memmove(buf, buf+total, n-total); n -= total
```

이 저장소 서버의 `serve_client` 가 정확히 이 구조다
([`slmp_stack.c:1151-1198`](../../stacks/slmp/src/slmp_stack.c), 길이 계산 `:1174-1182`,
처리 후 `memmove` `:1194-1195`). 버퍼가 가득 찼는데도 완결 프레임이 안 되면 연결을 끊는다
(`:1154-1157`). 서브헤더가 `50 00` 이 아닌 프레임은 `slmp_stack_handle_request` 가 `-EBADMSG` 를
반환하고, 서버는 **응답 없이 그 프레임을 버린다**(`:1185-1193`).

클라이언트는 응답을 하나만 기다리므로 더 단순하게 "9바이트 정확히 읽기 → 길이만큼 정확히 읽기"
(`recv_exact`, [`:621-642`](../../stacks/slmp/src/slmp_stack.c))로 충분하다.

### 6.4 타임아웃과 재연결

타임아웃은 두 겹이다.

| 타이머 | 누가 | 의미 |
|--------|------|------|
| 감시 타이머 (프레임 필드) | **PLC** | "이 요청을 처리하는 데 최대 X × 250 ms 까지 기다려라. 넘으면 에러 응답을 보내라." 타국 경유 시 특히 중요 |
| 소켓 타임아웃 | **클라이언트** | "응답이 Y ms 안에 안 오면 포기." 케이블 단선·PLC 정지 감지 |

**원칙: 소켓 타임아웃 > 감시 타이머 시간.** 그래야 PLC 가 보내는 "타임아웃 에러 응답"을
클라이언트가 받아볼 수 있다. pymcprotocol 도 소켓 타임아웃을 감시 타이머 + 1 초로 잡는다.

**원칙: 소켓 타임아웃이 나면 그 TCP 연결은 버리고 새로 연결한다.** 이유: 3E 는 ID 가 없으므로,
늦게 도착한 이전 요청의 응답이 다음 요청의 응답으로 오인된다.

> **이 저장소의 실제 동작 (부록 D-4, [검증]):**
> - 기본값이 감시 타이머 `0x0010`(4 초) / 소켓 타임아웃 1000 ms
>   ([`slmp_adapter.c:433-434`](../../adapters/slmp/slmp_adapter.c)) 로, 위 첫 원칙과 반대다.
> - 타임아웃 시 `client_transact` 는 `connected = 0` 만 설정하고 소켓을 닫지 않는다
>   ([`slmp_stack.c:656-660`](../../stacks/slmp/src/slmp_stack.c)). 다음 요청은 같은 소켓으로
>   나간다(`sockfd < 0` 만 검사, `:647`).
> - 스크래치 하네스로 재현: 첫 요청(D0 읽기)에 서버가 0.8 초 늦게 `0x1111` 로 답하고 클라이언트
>   타임아웃이 300 ms 일 때, 두 번째 요청(D1 읽기)의 결과로 **`0x1111`(D0 의 값)** 이 반환되었다.
>   ```
>   req1 (server answers 0x1111 late) rc=-110 connected=0
>   req2 for D1 (server answers 0x2222) rc=0 value=0x1111
>   ```
> - 재연결 로직은 스택·어댑터·코어 어디에도 없다. `slmp_stack_start` 는 `connect()` 때 한 번
>   호출되고([`slmp_adapter.c:531-542`](../../adapters/slmp/slmp_adapter.c)), 코어는
>   `fb_open`/`fb_reload` 에서만 `session_connect` 를 부른다
>   ([`core/fb_api.c:879`](../../core/fb_api.c), [`:950`](../../core/fb_api.c)).
>   PLC 가 연결을 끊으면(재부팅 등) 이후 모든 요청이 실패한다.
>
> 이 문서는 수정하지 않고 기록만 한다. 수정 방향은 11.3 절.

견고한 클라이언트 상태 기계:

```
        ┌──────────────┐  connect 성공   ┌───────────┐
 ──────▶│ DISCONNECTED │───────────────▶│ CONNECTED │◀─────────────┐
        └──────────────┘                └─────┬─────┘              │
            ▲    ▲ backoff 대기 후 재시도        │ 요청 전송          │ 응답 수신
            │    └───────────┐                 ▼                   │ (엔드코드 무관)
            │                │          ┌─────────────┐            │
            │ close()        │          │  WAIT_RESP  │────────────┘
            │                │          └──────┬──────┘
            │                │                 │ 소켓 타임아웃 / recv==0 / 파싱 불가
            └────────────────┴─────────────────┘  → 반드시 close() (stale 응답 방지)
```

- 엔드 코드 ≠ 0 은 **연결 문제가 아니다.** 연결은 유지하고 그 요청만 실패 처리한다.
- 재시도 간격은 지수 백오프(예: 0.5 s → 1 s → 2 s … 최대 10 s)로 PLC 에 부담을 주지 않는다.

### 6.5 감시 타이머 값 고르기

- 단위 250 ms, 2바이트 LE. `0x0000` = 무한 대기, `0x0001`~`0xFFFF` = 0.25 s ~ 약 4.5 시간.
- 매뉴얼은 자국 접근과 타국(네트워크 경유) 접근에 대해 권장 범위를 따로 제시한다
  (자국 수 초, 타국 수십 초 수준) **[정확한 권장 범위는 사양서 확인 필요]**.
- 실무 권장: 자국 CPU 직접 접근이면 `0x0004`~`0x0010`(1~4 초), 소켓 타임아웃은 그보다 0.5~1 초 길게.
- `0` 은 PLC 쪽에서 요청이 영원히 대기할 수 있어 권장하지 않는다. 이 저장소는 0 을 받으면
  `0x0010` 으로 바꾼다([`slmp_stack.c:274-276`](../../stacks/slmp/src/slmp_stack.c)) — 즉 이 저장소
  config 로는 "무한 대기"를 표현할 수 없다.

### 6.6 PLC 쪽 처리 타이밍 (왜 응답이 스캔 시간만큼 늦나)

PLC CPU 는 "입력 읽기 → 프로그램 실행 → 출력 → **END 처리**" 를 반복한다(한 바퀴 = 스캔).
내장 이더넷으로 들어온 SLMP 요청은 보통 **END 처리 때 서비스된다**. 그래서 응답 지연은 대략
"0 ~ 1 스캔 시간 + 네트워크 시간" 이고, 한 스캔에 처리하는 요청 수/시간에도 상한이 있다.
PLC 파라미터의 "서비스 처리 설정"(service processing setting)으로 이 시간을 조정할 수 있다
**[메뉴 이름·동작은 기종별 사양서 확인 필요]**.

설계상 의미: 스캔 10 ms 인 PLC 에 8 ms 주기로 포인트 5개를 따로따로 요청하면 따라가지 못한다.
여러 값은 **연속 주소에 모아 한 번의 일괄 요청으로** 읽고 쓰는 것이 SLMP 성능의 핵심이다.

> 이 저장소 어댑터는 포인트마다 별도 요청을 보낸다: `poll_cycle` 이 `access=write`(PLC→센서)
> 포인트마다 `remote_sync_read` 를 호출([`slmp_adapter.c:699-722`](../../adapters/slmp/slmp_adapter.c)),
> `write_point` 도 포인트마다 일괄 쓰기 1회([`:945-947`](../../adapters/slmp/slmp_adapter.c)).
> 요청마다 블로킹(최대 `timeout_ms`)이므로, 스케줄러 `cycle_ms`(예: 8 ms) 안에 끝나지 않으면
> `scheduler.c` 가 "cycle 초과" 경고를 낸다([`core/scheduler.c:44-51`](../../core/scheduler.c)).

### 6.7 서버(시뮬레이터) 측 처리

실제 제품에서 서버는 PLC 지만, 테스트·랩용으로 SLMP 서버를 직접 만들 일이 많다. 처리 순서:

```
accept()           → 연결 수 상한 / 출발지 IP 당 상한 검사
recv 누적          → 6.3 절 프레이밍
프레임 1개 도착     →
   서브헤더 = 50 00 ?        아니면: 폐기 (또는 연결 끊기)
   길이 ≥ 12 ?               아니면: 폐기
   커맨드 지원?              아니면: 엔드 코드 C059h (+ 에러 정보)
   서브커맨드 지원?          아니면: C059h
   디바이스 코드 알려짐?      아니면: 디바이스 오류 엔드 코드
   점수 1..최대?             아니면: C051h 계열
   범위 안?                  아니면: C056h
   쓰기면 데이터 길이 일치?   아니면: C061h (요구 데이터 길이 불일치)
   실행 → 응답 D0 00 + 에코 + 길이 + 0000 + 데이터
유휴 타임아웃       → 오랫동안 요청 없는 연결 정리
```

이 저장소 서버 구현 대응:

| 단계 | 코드 |
|------|------|
| accept + 전체 상한(`max_clients`) + IP 당 상한(`max_conn_per_ip`) | `server_accept` [`slmp_stack.c:1109-1149`](../../stacks/slmp/src/slmp_stack.c) |
| 논블로킹 수신 + 프레이밍 | `serve_client` [`:1151-1198`](../../stacks/slmp/src/slmp_stack.c) |
| 요청 해석/실행/응답 생성 | `slmp_stack_handle_request` [`:860-949`](../../stacks/slmp/src/slmp_stack.c) |
| 응답 헤더 (에코 포함) | `build_response` [`:836-858`](../../stacks/slmp/src/slmp_stack.c) |
| 유휴 연결 정리 (`idle_timeout_ms`, 기본 60 s) | `slmp_stack_poll` [`:1211-1220`](../../stacks/slmp/src/slmp_stack.c) |

저장소 서버의 사양 대비 차이: 쓰기 데이터 부족은 에러 응답 대신 **무응답 폐기**(`-EBADMSG`,
`:929-933`), 요구 데이터 길이 필드와 실제 커맨드 본문 길이의 일관성은 읽기 요청에 대해 검사하지
않음, 에러 정보 미포함, 비트 단위 니블 패킹 미준수(5.7 절), 비트 디바이스 워드 단위 접근 시 선두
번호를 워드 인덱스로 해석(부록 D-5).

## 7. 에러 처리, 제한값, PLC 쪽 설정

### 7.1 에러를 세 층으로 나눠 다루기

| 층 | 예 | 클라이언트 처리 |
|----|----|-----------------|
| 전송 (TCP) | connect 실패, 타임아웃, `recv()==0`(PLC 가 끊음), RST | 연결 폐기 → 백오프 재연결 |
| 프레임 | 서브헤더 불일치, 길이 이상, 에코 불일치 | 동기 상실로 간주 → 연결 폐기 |
| 애플리케이션 (엔드 코드) | `C056h` 범위 초과, `C059h` 미지원 커맨드, `4xxxh` CPU 에러 | 연결 유지, 해당 요청 실패로 보고. 설정 오류일 가능성 높음 → 로그에 엔드 코드와 에러 정보 기록 |

이 저장소의 매핑: 전송 오류는 음수 errno(`-ETIMEDOUT`, `-ECONNRESET` 등, `wait_fd`/`recv_exact`
[`slmp_stack.c:591-642`](../../stacks/slmp/src/slmp_stack.c)), 서브헤더 불일치는 `-EBADMSG`,
엔드 코드 ≠ 0 은 `LOG_WARN` 후 `-EIO`([`:745-749`](../../stacks/slmp/src/slmp_stack.c),
[`:828-832`](../../stacks/slmp/src/slmp_stack.c)). 마지막 에러 문자열은 어댑터 `health()` 로 노출된다
([`slmp_adapter.c:951-958`](../../adapters/slmp/slmp_adapter.c)). 단, 스택 내부 `last_error`
(`end_code=0x....`)는 어댑터의 `last_error` 와 별개라 `health()` 에는 어댑터 쪽 메시지
("poll <name> failed (-5)")만 보인다.

### 7.3 PLC 쪽 설정 (필수 체크)

SLMP 는 PLC 가 **서버 포트를 열어 줘야** 동작한다. 공장 출하 상태에서 바로 되는 경우는 드물다.
메뉴 이름은 소프트웨어 버전·기종별로 다르므로 개념 위주로 적는다 **[정확한 메뉴 경로는 해당
기종 매뉴얼 확인 필요]**.

| 설정 | iQ-R / iQ-F (GX Works3) | Q / L 내장 이더넷 (GX Works2) | 왜 필요한가 |
|------|------------------------|-------------------------------|-------------|
| IP 주소 | 모듈 파라미터 → 이더넷 포트 → 자국 설정 | PLC 파라미터 → 내장 이더넷 포트 설정 | 접속 대상 |
| 교신 데이터 코드 | Binary / ASCII 선택 | Binary / ASCII 선택 | 클라이언트 프레임과 반드시 일치 (이 저장소는 **Binary**) |
| 포트 열기 | "외부 기기 접속 구성"에 **SLMP 접속 기기** 추가, 프로토콜(TCP/UDP)·포트 지정 | "오픈 설정"에서 프로토콜 TCP/UDP, 오픈 방식 **MC 프로토콜**, 자국 포트 번호 | 이 포트로만 SLMP 요청을 받는다 |
| RUN 중 쓰기 허용 | "온라인 변경 허용/금지" 류 설정에서 SLMP 쓰기 허용 | "RUN 중 쓰기 허용 (FTP, MC 프로토콜)" 체크 | 끄면 RUN 중 쓰기 커맨드가 에러 엔드 코드로 거절됨 |
| 원격 패스워드 / IP 필터 | 보안 기능 | 원격 패스워드 | 설정 시 해제 커맨드 필요 (이 저장소 미지원) |
| 이더넷 모듈(QJ71E71 등) | — | 모듈 파라미터의 "운전 설정"에서 교신 데이터 코드, "RUN 중 쓰기 허용" | 모듈마다 별도 설정 |

그리고 파라미터를 **PLC 에 쓰고(write to PLC) 리셋/전원 재투입**해야 반영되는 항목이 많다.

### 7.4 현장 연결 전 체크리스트

1. PC → PLC `ping` 이 되는가? (같은 서브넷, 방화벽)
2. `nc -vz <plc_ip> <port>` 로 TCP 포트가 열리는가? (거부되면 7.3 의 포트 설정 확인)
3. 교신 데이터 코드가 Binary 인가?
4. 먼저 **읽기**(D0 1워드)로 성공 → 그 다음 쓰기. 쓰기가 에러면 "RUN 중 쓰기 허용" 확인.
5. 읽는 주소가 PLC 파라미터의 디바이스 점수 범위 안인가? (`C056h`)
6. X/Y/B/W 번호를 16진으로 줬는가? FX5 의 X/Y 는 8진.
7. 32비트/float/문자열 배치가 PLC 프로그램과 맞는가? (4.6 절, GX Works 디바이스 모니터로 확인)
8. 다른 클라이언트(HMI 등)가 같은 포트를 점유하고 있지 않은가? (TCP 포트당 연결 수 제한)

## 8. 직접 구현하기

이 장의 C 코드는 문서용으로 새로 쓴 **최소 구현**이며, 스크래치 디렉토리에서 컴파일·실행해
출력 바이트를 5장 예제와 대조했다 [검증]. 저장소 코드와는 별개다(저장소 코드는 9장).

### 8.1 로드맵 (마일스톤 + 검증 방법)

| # | 마일스톤 | 완료 기준 / 검증 방법 |
|---|----------|------------------------|
| M0 | LE 헬퍼(`put_le16/24`, `get_le16`) + hex 덤프 함수 | 단위 테스트: `put_le24(100000)` → `A0 86 01` |
| M1 | 디바이스 표 + 문자열 파서 (`"D100"`, `"X1A"`, `"XA"`) | 표 기반 테스트 (8.4 절 표), 알 수 없는 이름 거절 |
| M2 | 일괄 읽기 요청 인코더 (워드/비트) | 부록 B-1 과 바이트 단위로 일치 |
| M3 | 응답 파서 (서브헤더, 길이, 엔드 코드, 데이터/에러 정보 분리) | 부록 B 의 정상/이상 응답 hex 를 넣어 필드 확인 |
| M4 | 일괄 쓰기 인코더 (워드 LE, 비트 니블 패킹) | 부록 B-2, B-4 와 일치 |
| M5 | TCP 트랜잭션 (정확히 N바이트 송수신, 타임아웃 시 연결 폐기) | 느린 서버 시뮬로 stale 응답이 안 섞이는지 (8.7 절) |
| M6 | 서버/시뮬레이터: 디바이스 맵 + 요청 처리 + 에러 응답 | M2~M4 인코더로 만든 요청을 넣어 왕복. 에러 응답에 에러 정보 9B |
| M7 | TCP 서버 루프 (논블로킹, 프레이밍, 연결 상한, 유휴 타임아웃) | 반쪽 프레임 보내는 느린 클라이언트가 다른 클라이언트를 막지 않는지 |
| M8 | 값 매핑 계층 (int32/float/string/BCD, 스케일) | GX Works 디바이스 모니터 값과 대조 (4.6 절) |
| M9 | 실 PLC 연결 | 7.4 절 체크리스트, 읽기 → 쓰기 순, Wireshark 캡처 대조 |
| M10 | 견고성: 재연결 백오프, fuzz | libFuzzer 로 응답 파서/서버 요청 처리 (10.3 절) |

### 8.2 모듈 분해

```
┌─────────────────────┐   값/타입/엔디안/스케일. 프로토콜 모름
│  mapping (앱 계층)  │   "temperature = D110 * 0.1"
├─────────────────────┤
│  device table/parse │   "X1A" → (0x9C, 26, bit)
├─────────────────────┤
│  codec (순수 함수)  │   요청 인코드 / 응답 디코드. 소켓 모름 → 테스트 쉬움
├─────────────────────┤
│  transport          │   TCP connect / exact send·recv / 타임아웃 / 재연결
├─────────────────────┤
│  server (선택)      │   디바이스 맵 + handle_request(req) → resp (순수 함수로!)
└─────────────────────┘
```

요령: **`handle_request(bytes) → bytes` 를 소켓과 분리된 순수 함수로** 만들면, 테스트·fuzz·CTT 가 모두
TCP 없이 가능하다. 이 저장소도 `slmp_stack_handle_request` 를 그렇게 분리해 CTT 플러그인과 fuzz
하네스가 직접 호출한다(10장).

### 8.3 인코더/디코더 작성 요령

1. **오프셋 상수를 한 곳에**: `OFF_LEN = 7`, `OFF_CMD = 11`, `OFF_HEAD = 15` …
2. **길이 필드는 마지막에 계산**: 본문을 다 쓴 뒤 `len = total - 9` 로 채우면 실수가 없다.
3. **출력 버퍼 용량 검사**를 인코더 입구에서 한다 (`9 + len <= cap`).
4. **디코더는 입력을 절대 믿지 않는다**: `n >= 11`, `len >= 2`, `9 + len == n`(데이터그램/완결
   프레임 기준), 읽기 응답이면 데이터 길이 = 기대값.
5. **워드 데이터 표현을 하나로 정한다**: 내부에서는 `uint16_t[]` (호스트 정수)로 들고, 프레임에
   쓸 때만 LE 로 직렬화. (이 저장소는 내부 "canonical" 을 빅엔디안 바이트열로 들고 경계에서 LE 로
   바꾼다 — 9.4 절. 둘 다 가능하지만 섞으면 버그가 난다.)
6. **비트 단위 데이터는 니블 패킹** (5.7 절). 인코드/디코드 함수를 따로 두고 홀수 점수 테스트 필수.

최소 코덱 (C11 + POSIX `strncasecmp`):

```c
#include <errno.h>
#include <stdint.h>
#include <stdlib.h>
#include <string.h>
#include <strings.h>

static void put_le16(uint8_t *p, uint16_t v) { p[0] = (uint8_t)v; p[1] = (uint8_t)(v >> 8); }
static void put_le24(uint8_t *p, uint32_t v)
{
    p[0] = (uint8_t)v; p[1] = (uint8_t)(v >> 8); p[2] = (uint8_t)(v >> 16);
}
static uint16_t get_le16(const uint8_t *p) { return (uint16_t)(p[0] | (p[1] << 8)); }

/* 헤더 11바이트 (감시 타이머 포함) */
static void hdr(uint8_t *f, uint16_t req_len, uint16_t timer)
{
    f[0] = 0x50; f[1] = 0x00;   /* 서브헤더 3E 요청                 */
    f[2] = 0x00;                /* 네트워크 번호 (자국)             */
    f[3] = 0xFF;                /* PC 번호 (직결 CPU)               */
    put_le16(f + 4, 0x03FF);    /* 요구처 유닛 I/O (자국 CPU)       */
    f[6] = 0x00;                /* 멀티드롭 국번                    */
    put_le16(f + 7, req_len);   /* 오프셋 9 ~ 끝의 바이트 수        */
    put_le16(f + 9, timer);     /* 감시 타이머 (250 ms 단위)        */
}

static size_t enc_dev(uint8_t *f, uint16_t cmd, uint16_t sub,
                      uint32_t head, uint8_t code, uint16_t pts)
{
    put_le16(f + 11, cmd);
    put_le16(f + 13, sub);
    put_le24(f + 15, head);
    f[18] = code;
    put_le16(f + 19, pts);
    return 21;
}

/* 0401: 일괄 읽기 */
size_t slmp_read(uint8_t *f, uint32_t head, uint8_t code, uint16_t pts, int bit_unit)
{
    hdr(f, 12, 0x0010);
    return enc_dev(f, 0x0401, bit_unit ? 0x0001 : 0x0000, head, code, pts);
}

/* 1401/0000: 워드 일괄 쓰기 */
size_t slmp_write_words(uint8_t *f, uint32_t head, uint8_t code,
                        const uint16_t *w, uint16_t n)
{
    hdr(f, (uint16_t)(12 + 2 * n), 0x0010);
    size_t o = enc_dev(f, 0x1401, 0x0000, head, code, n);
    for (uint16_t i = 0; i < n; i++, o += 2) {
        put_le16(f + o, w[i]);
    }
    return o;
}

/* 1401/0001: 비트 일괄 쓰기 — 1바이트에 2점, 앞 점이 상위 니블 */
size_t slmp_write_bits(uint8_t *f, uint32_t head, uint8_t code,
                       const uint8_t *b, uint16_t n)
{
    uint16_t nbytes = (uint16_t)((n + 1) / 2);
    hdr(f, (uint16_t)(12 + nbytes), 0x0010);
    size_t o = enc_dev(f, 0x1401, 0x0001, head, code, n);
    memset(f + o, 0, nbytes);
    for (uint16_t i = 0; i < n; i++) {
        if (b[i]) {
            f[o + i / 2] |= (i % 2 == 0) ? 0x10 : 0x01;
        }
    }
    return o + nbytes;
}

/* 비트 일괄 읽기 응답 데이터 → 0/1 배열 */
void slmp_unpack_bits(const uint8_t *data, uint16_t n, uint8_t *out)
{
    for (uint16_t i = 0; i < n; i++) {
        out[i] = (i % 2 == 0) ? (data[i / 2] >> 4) & 1 : data[i / 2] & 1;
    }
}

/* 완결 응답 프레임 파싱. 반환: 엔드 코드(>=0) 또는 -errno.
 * data, dlen: 엔드 코드 뒤 바이트 (정상=읽은 데이터, 이상=에러 정보) */
int slmp_parse_resp(const uint8_t *f, size_t n, const uint8_t **data, size_t *dlen)
{
    if (n < 11 || f[0] != 0xD0 || f[1] != 0x00) {
        return -EBADMSG;
    }
    uint16_t len = get_le16(f + 7);
    if (len < 2 || n != 9u + len) {
        return -EBADMSG;
    }
    *data = f + 11;
    *dlen = len - 2u;
    return get_le16(f + 9);
}
```

### 8.4 디바이스 번호 문자열 파싱

가이드 문서에 나오는 표기를 `(코드, 번호, 비트여부)` 로 바꾸는 함수다. 요점:

- 디바이스 이름은 1~2글자. **가장 긴 이름부터 매칭**해야 `ZR`↔`Z`, `SB`↔`S`, `DX`↔`D` 가 구분된다.
- 16진 디바이스의 번호가 `A`~`F` 로 시작할 수 있다(`XA`, `BA0`, `SWFF`). "알파벳이 끝날 때까지가
  이름" 으로 자르면 `XA` 를 이름 `XA` 로 오인한다 → 이름 표에 있는 **가장 긴 접두사**로 잘라야 한다.
- 번호 기수는 디바이스별(4.3 절). FX5 X/Y 8진은 별도 처리.
- 번호 범위: Q 호환 3바이트 → `<= 0xFFFFFF`.

```c
typedef struct { const char *name; uint8_t code; uint8_t is_bit; uint8_t base; } dev_info;
static const dev_info DEVS[] = {
    {"X",0x9C,1,16}, {"Y",0x9D,1,16}, {"M",0x90,1,10}, {"L",0x92,1,10}, {"F",0x93,1,10},
    {"V",0x94,1,10}, {"B",0xA0,1,16}, {"D",0xA8,0,10}, {"W",0xB4,0,16}, {"TS",0xC1,1,10},
    {"TC",0xC0,1,10},{"TN",0xC2,0,10},{"SS",0xC7,1,10},{"SC",0xC6,1,10},{"SN",0xC8,0,10},
    {"CS",0xC4,1,10},{"CC",0xC3,1,10},{"CN",0xC5,0,10},{"SB",0xA1,1,16},{"SW",0xB5,0,16},
    {"S",0x98,1,10}, {"DX",0xA2,1,16},{"DY",0xA3,1,16},{"Z",0xCC,0,10}, {"R",0xAF,0,10},
    {"ZR",0xB0,0,10},{"SM",0x91,1,10},{"SD",0xA9,0,10},
};

int parse_device(const char *s, uint8_t *code, uint32_t *num, int *is_bit)
{
    const dev_info *best = NULL;
    size_t best_len = 0;
    for (size_t i = 0; i < sizeof DEVS / sizeof DEVS[0]; i++) {
        size_t n = strlen(DEVS[i].name);
        if (n > best_len && strncasecmp(s, DEVS[i].name, n) == 0) {
            best = &DEVS[i];
            best_len = n;
        }
    }
    if (!best || !s[best_len]) {
        return -EINVAL;
    }
    char *end;
    errno = 0;
    unsigned long v = strtoul(s + best_len, &end, best->base);
    if (*end || errno || v > 0xFFFFFF) {
        return -EINVAL;
    }
    *code = best->code;
    *num = (uint32_t)v;
    if (is_bit) {
        *is_bit = best->is_bit;
    }
    return 0;
}
```

### 8.5 TCP 트랜잭션 (타임아웃 시 반드시 연결 폐기)

```c
typedef struct { int fd; char ip[64]; int port; int timeout_ms; } slmp_conn_t;

/* poll 로 대기하며 정확히 n 바이트 송신/수신 */
static int io_exact(int fd, uint8_t *b, size_t n, int ms, int is_send);
static int conn_open(slmp_conn_t *c);   /* socket + TCP_NODELAY + connect */
static void conn_close(slmp_conn_t *c); /* close(fd); fd = -1 */

/* 요청 1개 → 응답 1개. 전송/프레이밍 오류가 나면 무조건 연결을 닫는다.
 * 그래야 늦게 도착한 응답이 다음 요청의 응답으로 오인되지 않는다. */
int slmp_transact(slmp_conn_t *c, const uint8_t *req, size_t req_len,
                  uint8_t *resp, size_t cap, size_t *resp_len)
{
    int rc;
    if (c->fd < 0 && (rc = conn_open(c)) != 0) {
        return rc;
    }
    if ((rc = io_exact(c->fd, (uint8_t *)req, req_len, c->timeout_ms, 1)) != 0) {
        goto fail;
    }
    if (cap < 9) {
        rc = -ENOSPC;
        goto fail;
    }
    if ((rc = io_exact(c->fd, resp, 9, c->timeout_ms, 0)) != 0) {
        goto fail;
    }
    /* 서브헤더 + 에코(네트워크/PC/I/O/멀티드롭) 검사 */
    if (resp[0] != 0xD0 || resp[1] != 0x00 || memcmp(resp + 2, req + 2, 5) != 0) {
        rc = -EBADMSG;
        goto fail;
    }
    size_t len = (size_t)(resp[7] | (resp[8] << 8));
    if (len < 2 || 9 + len > cap) {
        rc = -EBADMSG;
        goto fail;
    }
    if ((rc = io_exact(c->fd, resp + 9, len, c->timeout_ms, 0)) != 0) {
        goto fail;
    }
    *resp_len = 9 + len;
    return 0;   /* 엔드 코드 해석은 호출자 몫 (연결 문제 아님) */
fail:
    conn_close(c);
    return rc;
}
```

### 8.6 서버 요청 처리 의사코드

```
handle_request(req, n) -> resp or DROP:
    if n < 21 or req[0..1] != 50 00:            return DROP        # 또는 연결 끊기
    len = le16(req+7);  if 9+len != n:          return DROP
    cmd = le16(req+11); sub = le16(req+13)
    if cmd not in {0401, 1401}:                 return err(C059)
    if sub not in {0000, 0001}:                 return err(C059)
    head = le24(req+15); code = req[18]; pts = le16(req+19)
    dev = lookup(code);  if !dev:               return err(<디바이스 오류 코드>)
    if sub == 0001 and dev.is_word:             return err(C05C)   # 워드 디바이스를 비트 단위로 [사양서 확인]
    if pts == 0 or pts > (sub==0000 ? 960 : 7168): return err(C051)
    if head + span(pts, sub, dev) > dev.size:   return err(C056)
    if cmd == 0401:
        data = sub==0000 ? words_le(dev, head, pts) : nibble_pack(bits(dev, head, pts))
        return ok(data)
    else:
        need = sub==0000 ? 2*pts : ceil(pts/2)
        if n - 21 != need:                      return err(C061)
        write(...);  return ok(empty)

err(code) = D0 00 | req[2..6] | le16(11) | le16(code) | req[2..6] | le16(cmd) | le16(sub)
ok(data)  = D0 00 | req[2..6] | le16(2+len(data)) | 00 00 | data
```

`span()` 주의: 비트 디바이스를 **워드 단위**로 읽으면 선두 번호는 비트 번호이고, 범위는
`head .. head + 16*pts - 1` 비트다.

### 8.7 동시성

| 상황 | 권장 |
|------|------|
| 클라이언트가 여러 스레드에서 요청 | 연결마다 뮤텍스로 "송신~응답 수신" 구간 전체를 잠근다. 또는 전용 I/O 스레드 + 큐 |
| 처리량이 부족 | (1) 주소를 모아 일괄 요청 수를 줄인다 (2) 연결을 여러 개 (3) 4E + 파이프라인 |
| 서버 | 논블로킹 소켓 + `poll`/`epoll`. 한 클라이언트의 반쪽 프레임 때문에 전체가 막히면 안 된다 |
| 서버 디바이스 맵 | 요청 처리와 앱 쓰기가 다른 스레드면 맵에 락. "워드 N개 쓰기"가 원자적으로 보이게 |
| 비트 하나만 바꾸기 (D300.3) | 클라이언트 쪽 read-modify-write 는 **원자적이지 않다**. PLC 가 그 사이 같은 워드를 바꾸면 덮어쓴다. 가능하면 비트 디바이스(M 등)를 쓰거나 워드 전체를 한쪽만 소유하게 설계 |

이 저장소: 스택은 락이 없고 단일 스레드 사용을 전제한다. 코어가 `rt->mu` 로 `poll_cycle` 과 앱
호출(`fb_read_point`/`fb_write_point`)을 직렬화한다([`core/fb_api.c:750-756`](../../core/fb_api.c),
[`:986`](../../core/fb_api.c), [`:1059`](../../core/fb_api.c)). 서버는 논블로킹 + 느린 클라이언트
격리 테스트가 있다(`test_g7_slmp_idle_per_ip_and_slow`,
[`tests/test_slmp_stack.c:426-543`](../../tests/test_slmp_stack.c)).

### 9.2 코어가 어댑터를 구동하는 방식

### 9.3 access 방향과 데이터 흐름

`access` 는 **PLC 관점**이다(Modbus/PROFINET 어댑터와 같은 어휘).

| `access` | PLC 입장 | 클라이언트 모드 동작 |
|----------|----------|----------------------|
| `read` (기본) | PLC 가 읽을 값 (센서가 제공) | 앱 `write_point` → 캐시 갱신 → **PLC 에 일괄 쓰기** |
| `write` | PLC 가 쓴 값 (센서가 소비) | `poll_cycle` 과 `read_point` 때 **PLC 에서 일괄 읽기** → 캐시 |
| `readwrite`/`rw` | 양방향 | 둘 다 |

```
write_point("temperature", 25.5)                     poll_cycle()
   │ scale: raw = (25.5-offset)/0.1 = 255              │ access=write 포인트마다
   │ slmp_encode_number → canonical BE [00 FF]         │ remote_sync_read
   │ endian 적용 → 창                                   │   slmp_stack_client_batch_read
   │ write_map_window → 로컬 맵 D110                    │     0401 요청 → 응답 LE → BE 창
   │ remote_sync_write                                 │     → 로컬 맵 갱신
   │   slmp_stack_client_batch_write                   ▼
   │     BE 창 → LE 워드 → 1401 요청                 read_point("plc_trigger")
   ▼                                                   → 로컬 맵에서 창 읽기 → 변환 → 앱
  PLC D110 = 0x00FF
```

서버 모드(`role: "server"`)에서는 PLC 통신 없이 로컬 맵만 읽고 쓰며, 외부 SLMP 클라이언트가 그 맵에
접근한다(랩 시뮬레이터, [`config/example.fake_sensor.slmp.json`](../../config/example.fake_sensor.slmp.json)).

**points** (`address.slmp` 하위)

| 포인트 | 설정 | 실제로 PLC 와 주고받는 것 |
|--------|------|---------------------------|
| `barcode_value` | `string`, `length: 32`, D100 | 16워드(`D100~D115`) 일괄 쓰기. 문자 배치는 11.1 절 주의 |

| `pressure` | `float`, `endian: "CDAB"`, D200, quantity 2 | D200=하위 워드, D201=상위 워드 → **MELSEC 관례(4.6)와 일치** [검증] |
| `plc_trigger` | `bool`, M10, `unit: "bit"` | M10 1점 **비트 단위** 읽기. 1점 읽기는 우연히 동작하지만(부록 D-1) 같은 형태의 쓰기·다점 접근은 실 PLC 와 비호환 |
| `alarm_bit` | `bool`, D300, `bit: 3` | D300 1워드 읽고 bit3 추출 |
| `input_x` | `bool`, X, `start: "1A"`, `unit: "bit"` | X1A(=26) 1점 비트 단위 읽기 (부록 D-1 의 1점 예외로 동작) |

엔디안 어휘 (저장소 canonical 은 "워드마다 상위 바이트 먼저"인 BE 바이트 창):

| `endian` | 32비트 값 0xAABBCCDD 의 배치 | MELSEC 관례와 비교 |
|----------|-------------------------------|--------------------|
| `ABCD` (기본) | D(n)=`AABB`, D(n+1)=`CCDD` (상위 워드 먼저) | **반대** — `DMOV`/`EMOV` 와 워드 순서가 다름 |
| `CDAB` | D(n)=`CCDD`, D(n+1)=`AABB` | **일치** (int32/float 는 이것을 쓸 것) |
| `BADC` / `DCBA` | 워드 안 바이트까지 뒤집음 | 타사 장비용 |

실측 [검증] (서버 모드 어댑터에 `write_point` 후 외부 클라이언트로 읽은 프레임 데이터):

```
int32 0x00010002, endian ABCD → D210=0x0001 D211=0x0002 (wire 01 00 02 00)
int32 0x00010002, endian CDAB → D220=0x0002 D221=0x0001 (wire 02 00 01 00)   ← MELSEC DINT
float 1.5,        endian CDAB → D200=0x0000 D201=0x3FC0 (wire 00 00 C0 3F)   ← MELSEC REAL
```

주소 표기 별칭: `device_code`(`device`, `dev`, `soft_device`), `start`(`address`, `head`, `addr`,
`register`), `quantity`(`count`, `qty`), `offset`(`reg_offset`, start 에 더함), `bit`(`bit_offset`,
`bit_index`), `bit_count`, `unit`(`access_unit`). 포인트 최상위의 `offset` 은 **공학값 오프셋**
(eng = raw × scale + offset)이고 `address.slmp.offset` 은 **레지스터 오프셋**이다 — 같은 이름,
다른 의미이므로 주의([`slmp_adapter.c:300`](../../adapters/slmp/slmp_adapter.c) vs [`:367-370`](../../adapters/slmp/slmp_adapter.c)).

`unit` 을 생략하면: `bool` + 비트 디바이스 + `bit` 미지정이면 비트 단위, 그 외는 워드 단위
([`slmp_adapter.c:380-390`](../../adapters/slmp/slmp_adapter.c)).

### 9.5 디바이스 문자열 파싱의 실제 동작 (`parse_device_head`)

[`slmp_adapter.c:132-193`](../../adapters/slmp/slmp_adapter.c):

1. `device_code` 가 있으면 먼저 그것으로 코드 결정.
2. `start` 문자열의 **앞쪽 알파벳을 전부** 디바이스 이름으로 떼어 낸다(`:149-163`).
3. 나머지를 번호로: 16진 디바이스면 base 16, `0x` 접두면 auto, 그 외 10진(`:168-176`).

실측 [검증]:

| 입력 | 결과 |
|------|------|
| `"start": "X1A"` | OK, X 26 |
| `"device_code": "X", "start": "1A"` | OK, X 26 |
| `"start": "XA"` | **실패** — `"XA"` 전체를 이름으로 보고 알 수 없는 디바이스 → 포인트 건너뜀 |
| `"device_code": "X", "start": "A"` | **실패** — `"A"` 를 디바이스 이름으로 보려다 실패 |
| `"start": "X0A"` / `"0xA"` / 숫자 `10` | OK (우회책) |

즉 16진 번호가 `A`~`F` 로 시작하면 앞에 `0` 을 붙여야 한다(`XA` → `X0A`, `BA0` → `B0A0`).
실패 시 `LOG_WARN "point %s 주소 파싱 실패 - 건너뜀"` 만 남고 init 은 성공하므로, 포인트가 조용히
사라진다는 점도 주의(부록 D-6). 또한 X/Y 를 항상 16진으로 보므로 FX5(8진) 주소 문자열은 틀린
번호가 된다.

### 10.3 Fuzz

[`tests/fuzz/fuzz_slmp_request.c`](../../tests/fuzz/fuzz_slmp_request.c) 는 libFuzzer 하네스로, 첫
바이트로 모드를 골라(`:143`) 원시 바이트(0), 워드 읽기(1), 워드 쓰기(2), 비트 R/W(3), 미구현
커맨드(4: `0403`/`1402`/`0801`/`0402`), 미지 디바이스·서브커맨드(5), 점수 경계·짧은 쓰기(6),
상태 있는 쓰기→읽기(7) 를 `slmp_stack_handle_request` 에 넣는다. 사전은
[`tests/fuzz/dict/slmp_request.dict`](../../tests/fuzz/dict/slmp_request.dict), 코퍼스는
`tests/fuzz/corpus/slmp_request/`.

```sh
CC=clang cmake -S . -B build-fuzz -DBUILD_FUZZERS=ON -DBUILD_DAEMON=OFF -DBUILD_CTT=OFF
cmake --build build-fuzz --target fuzz_slmp_request
./build-fuzz/fuzz_slmp_request -max_total_time=60 \
    -dict=tests/fuzz/dict/slmp_request.dict tests/fuzz/corpus/slmp_request
```

(필자 환경에서는 clang 의 libFuzzer 런타임(`libclang_rt.fuzzer`)이 없어 링크 단계에서 실패해 실행하지
못했다 — 환경 문제이며 하네스 코드는 읽기로만 확인.)

직접 구현한다면 fuzz 대상은 두 곳이다: **서버의 요청 처리**(외부 입력)와 **클라이언트의 응답 파서**
(PLC 나 중간자가 보낸 입력). 이 저장소 fuzz 는 앞의 것만 다룬다.

### 10.5 Wireshark

- **2026-09 기준 Wireshark 본선(GitLab master 의 `epan/dissectors/` 파일 목록)에는 SLMP/MC 프로토콜
  전용 디섹터가 없다.** (필자가 파일 목록을 조회해 `slmp`/`melsec`/`mcprotocol` 이름을 찾지 못함.)
  그래서 캡처하면 그냥 "TCP payload" 로 보인다.
- 캡처 필터: `tcp port 5000` (PLC 에서 연 포트로). 디스플레이 필터: `tcp.port == 5000 && tcp.len > 0`.
- 페이로드 첫 두 바이트로 방향을 즉시 구분: `50 00` 요청, `D0 00` 응답.
- 편하게 보려면 Lua 디섹터를 쓴다. 아래는 **스케치**다 (필자 환경에 Wireshark 가 없어 실행 검증 못 함):

```lua
-- slmp3e.lua : Wireshark → Help → About → Folders → Personal Lua Plugins 에 복사
local p = Proto("slmp3e", "SLMP Binary 3E")
local F = p.fields
F.sub  = ProtoField.bytes ("slmp3e.subheader", "Subheader")
F.net  = ProtoField.uint8 ("slmp3e.net",   "Network No.", base.HEX)
F.pc   = ProtoField.uint8 ("slmp3e.pc",    "PC No.",      base.HEX)
F.io   = ProtoField.uint16("slmp3e.io",    "Dest module I/O", base.HEX)
F.md   = ProtoField.uint8 ("slmp3e.md",    "Multidrop",   base.HEX)
F.len  = ProtoField.uint16("slmp3e.len",   "Data length")
F.tmr  = ProtoField.uint16("slmp3e.timer", "Monitoring timer (x250ms)")
F.cmd  = ProtoField.uint16("slmp3e.cmd",   "Command",     base.HEX)
F.sc   = ProtoField.uint16("slmp3e.subcmd","Subcommand",  base.HEX)
F.head = ProtoField.uint24("slmp3e.head",  "Head device No.")
F.dev  = ProtoField.uint8 ("slmp3e.dev",   "Device code", base.HEX)
F.pts  = ProtoField.uint16("slmp3e.points","Points")
F.end_ = ProtoField.uint16("slmp3e.end",   "End code",    base.HEX)

local function one(tvb, pinfo, tree)
  local t = tree:add(p, tvb())
  local is_req = tvb(0,1):uint() == 0x50
  t:add(F.sub, tvb(0,2)); t:add(F.net, tvb(2,1)); t:add(F.pc, tvb(3,1))
  t:add_le(F.io, tvb(4,2)); t:add(F.md, tvb(6,1)); t:add_le(F.len, tvb(7,2))
  if is_req and tvb:len() >= 21 then
    t:add_le(F.tmr, tvb(9,2)); t:add_le(F.cmd, tvb(11,2)); t:add_le(F.sc, tvb(13,2))
    t:add_le(F.head, tvb(15,3)); t:add(F.dev, tvb(18,1)); t:add_le(F.pts, tvb(19,2))
    pinfo.cols.info = string.format("SLMP req cmd=%04X", tvb(11,2):le_uint())
  elseif not is_req and tvb:len() >= 11 then
    t:add_le(F.end_, tvb(9,2))
    pinfo.cols.info = string.format("SLMP resp end=%04X", tvb(9,2):le_uint())
  end
end

function p.dissector(buf, pinfo, tree)
  pinfo.cols.protocol = "SLMP3E"
  local off = 0
  while off < buf:len() do
    local rem = buf:len() - off
    if rem < 9 then
      pinfo.desegment_offset = off; pinfo.desegment_len = DESEGMENT_ONE_MORE_SEGMENT
      return buf:len()
    end
    local total = 9 + buf(off + 7, 2):le_uint()
    if rem < total then
      pinfo.desegment_offset = off; pinfo.desegment_len = total - rem
      return buf:len()
    end
    one(buf(off, total):tvb(), pinfo, tree)
    off = off + total
  end
  return off
end
DissectorTable.get("tcp.port"):add(5000, p)
```

Wireshark 없이 빠르게 보려면 `tcpdump -i any -X 'tcp port 5000'` 로 hex 를 뜨고 부록 B 와 비교한다.

### 10.6 이 문서의 hex 를 재현하는 법

문서의 [검증] 값은 저장소에 파일을 추가하지 않고, 스크래치 디렉토리의 작은 C 파일로 만들었다.

```c
/* harness.c — cc -std=c11 -D_GNU_SOURCE -Istacks/slmp/include -Iinclude -Icore \
 *             harness.c build/libslmp_stack.a -lpthread */
#include "slmp_stack.h"
#include <stdio.h>
#include <string.h>
static void dump(const char *t, const uint8_t *b, size_t n)
{
    printf("%-10s", t);
    for (size_t i = 0; i < n; i++) printf(" %02X", b[i]);
    printf("\n");
}
int main(void)
{
    slmp_cfg_t cfg; memset(&cfg, 0, sizeof cfg);
    cfg.role = SLMP_ROLE_SERVER; cfg.frame = SLMP_FRAME_3E_BINARY;
    cfg.pc_no = 0xFF; cfg.dest_module_io = 0x03FF; cfg.monitoring_timer = 0x0010;
    slmp_stack_t *s = slmp_stack_create(&cfg);
    uint16_t seed[2] = {0x1234, 0xABCD};
    slmp_stack_write_words(s, SLMP_DEV_D, 100, seed, 2);
    slmp_range_t r = {.addr = {.device_code = SLMP_DEV_D, .head = 100,
                               .unit = SLMP_ACCESS_WORD}, .quantity = 2};
    uint8_t req[64], resp[64]; size_t rl, sl;
    slmp_encode_batch_read(&cfg, &r, req, sizeof req, &rl);  dump("REQ", req, rl);
    slmp_stack_handle_request(s, req, rl, resp, sizeof resp, &sl); dump("RES", resp, sl);
    slmp_stack_destroy(s);
    return 0;
}
```

주의: `slmp_encode_batch_*` 는 넘겨받은 `cfg` 를 **그대로** 쓴다. `slmp_stack_create` 가 채우는
기본값(`dest_module_io=0x03FF`, 감시 타이머 16)은 스택 내부 사본에만 적용되므로, 0 으로 초기화한
구조체를 그대로 인코더에 넘기면 I/O 번호 `00 00`, 타이머 `00 00` 인 프레임이 나온다. 인코더에는
`slmp_stack_cfg(s)` 가 돌려주는 설정을 넘기는 것이 안전하다.

### 10.7 실 PLC 연결 시 체크

| 증상 | 의심 | 확인 |
|------|------|------|
| connect 거부 (RST) | 포트 미개방 / 프로토콜 TCP·UDP 불일치 | 7.3 포트 설정, `nc -vz` |
| connect 타임아웃 | IP/서브넷/방화벽 | `ping`, 스위치 링크 |
| 연결은 되는데 응답 없음 | 교신 데이터 코드 ASCII 로 설정됨, 또는 3E 가 아닌 프레임 기대 | PLC 파라미터 |
| `C056h` | 디바이스 범위 초과 | PLC 파라미터의 디바이스 점수, 16진/10진 착오 |
| `C059h` | 미지원 커맨드 (예: iQ-R 확장을 Q 에) | 서브커맨드 |
| 쓰기만 에러 | RUN 중 쓰기 금지 | 7.3 "RUN 중 쓰기 허용" |
| 값이 뒤집혀 보임 (`0x3412`) | LE 처리 누락 | 4.6 / 0.4 |
| float 이 이상한 값 | 워드 순서 (ABCD vs CDAB) | 4.6, 9.4 |
| 문자열이 두 글자씩 뒤바뀜 (`BADC`) | 워드 내 문자 순서 | 11.1 |
| 비트가 항상 OFF / 엉뚱한 비트가 바뀜 | 니블 패킹 미준수 | 5.7, 부록 D-1 |
| 주기적으로 엉뚱한 주소의 값 | 타임아웃 후 stale 응답 | 6.4 |

GX Works 의 이더넷 진단(Ethernet diagnostics) 화면에서 연결 상태·수신 에러 코드를 볼 수 있다
**[메뉴 위치 기종별 확인 필요]**. PLC 가 기록한 에러 코드는 SD 영역(예: SD0 최신 자기진단 에러 코드)에서도
읽을 수 있다 **[주소 기종별 확인 필요]**.

## 11. 흔한 함정과 보안 고려사항

### 11.1 흔한 함정

1. **리틀엔디안을 잊음.** `0x0401` 을 `04 01` 로 보내면 PLC 는 커맨드 `0104h` 로 읽고 `C059h`.
2. **서브헤더를 LE 수치로 생각함.** "0x5000 을 LE 로" 보내면 `00 50` 이 되어 무응답. 고정 바이트 `50 00`.
3. **길이 필드 범위 착오.** 요청 길이는 감시 타이머부터 센다(헤더 9바이트 제외). 읽기 요청은 항상 12.
4. **X/Y/B/W 를 10진으로 해석.** `X100` 은 256번. FX5 X/Y 는 8진.
5. **비트 단위 데이터를 1바이트/점으로 처리.** 사양은 니블 패킹(5.7).
6. **워드 순서.** MELSEC 의 32비트/float 는 하위 워드가 앞 번호(이 저장소 어휘 `CDAB`). 기본값
   `ABCD` 로 두면 PLC 의 `DMOV`/`EMOV` 결과와 워드가 뒤바뀐다.
7. **문자열 바이트 순서.** MELSEC `$MOV` 관례는 앞 문자가 하위 바이트(D100=`4241h` 에 "AB").
   이 저장소 어댑터의 기본(`string_swap: false`)은 앞 문자를 **상위** 바이트에 넣는다
   ([`slmp_codec.c:442-445`](../../adapters/slmp/slmp_codec.c)). 실측 [검증]: `"ABCD"` 를 기본값으로
   쓰면 D100=`4142h`, D101=`4344h`(와이어 `42 41 44 43`), `string_swap: true` 면 D100=`4241h`(와이어
   `41 42 43 44`). PLC 래더가 `$MOV`/문자열 명령으로 다루는 값이면 `string_swap: true` 가 맞고,
   예제 config 의 `barcode_value` 는 이를 지정하지 않으므로 PLC 쪽 가이드와 대조해 결정해야 한다.
   (반대로 PLC 가이드가 "상위 바이트가 첫 문자"라고 정의한 장비도 있어 옵션으로 둔 것이다.)
8. **타임아웃 후 같은 연결 재사용.** 3E 는 ID 가 없어 이전 응답이 섞인다(6.4).
9. **소켓 타임아웃 < 감시 타이머.** PLC 의 타임아웃 에러 응답을 못 받고 stale 이 된다.
10. **작은 요청 폭탄.** 포인트마다 1 요청 → PLC 스캔 시간에 묶여 주기를 못 맞춤. 연속 주소로 모아 일괄 요청.
11. **워드 내 비트 쓰기(read-modify-write) 경합.** PLC 도 같은 워드를 쓰면 덮어씀.
12. **포트 공유.** TCP 포트 하나를 HMI 가 이미 점유 → 연결 거부. PLC 에 포트를 여러 개 연다.
13. **TCP 에서 `recv` 한 번 = 프레임 하나라고 가정.** 반쪽/두 개가 올 수 있다(6.3).
14. **저장소 특유:** `"XA"`, `"BA0"` 처럼 A~F 로 시작하는 16진 번호 문자열은 파싱 실패 후 포인트가 조용히
    빠진다(9.5). `X0A` 로 쓸 것.
15. **저장소 특유:** 인코더에 기본값이 채워지지 않은 `cfg` 를 넘기면 `03FF`/타이머가 0 인 프레임(10.6).

### 11.2 스케일/타입 관련 함정 (이 저장소 어댑터)

- 스케일이 설정된 포인트의 앱 값은 **float32 빅엔디안 4바이트**로 교환된다
  ([`slmp_adapter.c:840-863`](../../adapters/slmp/slmp_adapter.c), [`:886-905`](../../adapters/slmp/slmp_adapter.c)).
- `bool` + `bit` 지정 포인트 쓰기는 클라이언트 모드에서 먼저 PLC 에서 워드를 읽어 온 뒤 비트만 바꿔 다시
  쓴다([`slmp_adapter.c:927-933`](../../adapters/slmp/slmp_adapter.c) → `write_map_window` 의 RMW
  [`:617-647`](../../adapters/slmp/slmp_adapter.c)). 11.1-11 의 경합이 그대로 적용된다.

### 11.4 보안

- **SLMP(3E/4E)에는 인증도 암호화도 없다.** 네트워크에 닿는 누구든 포트만 알면 디바이스를 읽고 쓸 수
  있고, 기종/설정에 따라 원격 RUN/STOP 까지 가능하다. 평문이므로 스니핑·변조·재전송에 무방비다.
- PLC 측 완화책(기종별 **[사양서 확인 필요]**): 원격 패스워드(원격 패스워드 해제 커맨드 필요), IP 필터,
  "RUN 중 쓰기 금지", 포트를 필요한 것만 개방, 불필요 프로토콜 비활성화.
- 네트워크 측: 제어망 분리(VLAN/방화벽), 인터넷 직접 노출 금지, 원격 접속은 VPN, IEC 62443 존/콘딧 설계.
- MELSEC 이더넷 기능에 대해서는 과거 여러 공개 보안 권고(DoS, 인증 우회 등)가 있었다. 구체 항목은
  Mitsubishi Electric PSIRT 와 CISA ICS 권고로 확인할 것(번호는 여기서 단정하지 않는다).
- 이 저장소 서버(시뮬레이터)의 방어: 연결 수 상한, 출발지 IP 당 상한, 유휴 타임아웃, 프레임 최대 2048B,
  점수 상한, 알 수 없는 디바이스 코드에 대해 맵을 새로 할당하지 않음(`slmp_device_known` 검사
  [`slmp_stack.c:884`](../../stacks/slmp/src/slmp_stack.c)). 그러나 **인증은 없으므로 랩 외부에 노출하지 말 것.**
- 클라이언트로서의 방어: 응답 길이 필드가 버퍼보다 크면 거절(`client_transact` [`:667-669`](../../stacks/slmp/src/slmp_stack.c)),
  다만 이때 남은 바이트를 읽지 않고 연결도 유지하므로 동기가 깨진다(11.3 의 연결 폐기로 해결).

## 12. 인증/적합성

- SLMP/CC-Link 계열의 적합성(conformance)은 **CLPA(CC-Link Partner Association)** 가 관리한다.
  CC-Link IE Field / TSN / Field Network Basic 제품은 CLPA 적합성 시험 대상이다. SLMP 대응 기기 단독의
  인증 프로그램 유무·절차는 CLPA 에 확인해야 한다 **[확인 필요]**.
- Mitsubishi 쪽에는 파트너 프로그램(e-F@ctory Alliance 등)이 있으나 이는 프로토콜 인증과는 별개다.
- **이 저장소의 CTT green 은 인증이 아니다.** [`docs/ctt_slmp_bundle.md`](../ctt_slmp_bundle.md) 와
  [`docs/ctt_slmp_matrix.md`](../ctt_slmp_matrix.md) 가 명시하듯 `SLMP-3E-*` ID 는 내부 라벨이고,
  공인 랩 판정·공식 TC 번호를 대체하지 않는다. 또한 10.1 절처럼 자기 일관성 테스트라 실 PLC 호환성도
  보증하지 않는다(부록 D).
- 실무적 "적합성" 확인 방법: 대상 PLC 기종(가능하면 Q, iQ-R, FX5 각각)과 실제로 연결해 부록 B 의 요청을
  보내고 응답을 캡처해 golden 으로 보관한다.

## 부록 A. 구현 체크리스트

**코덱**

- [ ] 모든 다바이트 수치 LE, 서브헤더는 고정 바이트 `50 00` / `D0 00`
- [ ] 요청 길이 = 오프셋 9 부터 끝 (읽기 = 12, 워드 쓰기 = 12 + 2n, 비트 쓰기 = 12 + ceil(n/2))
- [ ] 선두 번호 3바이트 LE, `<= 0xFFFFFF`
- [ ] 서브커맨드 `0000` 워드 / `0001` 비트
- [ ] 비트 데이터 니블 패킹 (앞 점 = 상위 니블), 홀수 점수 패딩
- [ ] 점수 상한 (워드 960, 비트 7168 — 기종 확인)
- [ ] 응답: 서브헤더, `9 + len == n`, `len >= 2`, 엔드 코드, 정상 데이터 길이 검사
- [ ] 이상 응답의 에러 정보 9바이트를 데이터로 오해하지 않음
- [ ] 디바이스 문자열 파서: 최장 접두사, 디바이스별 기수, FX5 8진 처리

**전송 (클라이언트)**

- [ ] 연결당 요청 1개씩 (또는 4E 시리얼)
- [ ] 정확히 9바이트 → 길이만큼 수신
- [ ] 소켓 타임아웃 > 감시 타이머
- [ ] 타임아웃/프레이밍 오류 시 연결 폐기, 백오프 재연결
- [ ] 엔드 코드 ≠ 0 은 연결 유지
- [ ] 에코 필드 확인
- [ ] `TCP_NODELAY` (작은 요청 지연 방지)

**서버 / 시뮬레이터**

- [ ] 논블로킹 + 프레이밍 버퍼, 최대 프레임 크기
- [ ] 연결 수 / IP 당 / 유휴 타임아웃 상한
- [ ] 미지원 커맨드 `C059h`, 점수 `C051h`, 범위 `C056h`, 길이 불일치 `C061h` (+ 에러 정보)
- [ ] 비트 디바이스 워드 단위 접근: 선두 = 비트 번호
- [ ] `handle_request` 는 순수 함수 → 단위 테스트/fuzz

**값 매핑**

- [ ] int32/float: 하위 워드 먼저 (MELSEC)
- [ ] 문자열: 앞 문자 하위 바이트 (MELSEC `$MOV`), 옵션으로 반대
- [ ] BCD, 스케일/오프셋, 워드 내 비트필드

**운영**

- [ ] PLC 포트/프로토콜/교신 데이터 코드/RUN 중 쓰기 허용 설정
- [ ] 제어망 분리, 인터넷 비노출
- [ ] 실 PLC golden 캡처 확보

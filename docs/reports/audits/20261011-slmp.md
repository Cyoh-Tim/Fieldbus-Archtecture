## A20261011-3. 클라이언트 스택이 로컬 맵 밖 주소의 쓰기를 PLC 로 보내지 않는다

**문제:** 스택은 클라이언트 역할에서도 모든 일괄 쓰기를 먼저 로컬 맵(서버 시뮬용 디바이스 메모리, 기본 워드 디바이스 4096 워드,
비트 디바이스 8192 비트 = 512 워드)에 쓰고, 그 쓰기가 실패하면 **PLC 에 요청을 보내지 않고** `-ERANGE` 를 돌려준다.
맵 크기는 PLC 의 디바이스 범위와 무관한 구현 상수다. 그래서 기본 설정에서

- 워드 디바이스 번호 4096 이상 (D5000, 16진 W1000 이상, R/ZR 대부분),
- 비트 디바이스 비트 단위 번호 8192 이상,
- 비트 디바이스 워드 단위 선두 512 이상 (예: M512. T10-6 의 "선두를 워드 인덱스로 해석" 이 클라이언트 캐시에도 쓰여서
  M512 워드 = 맵 워드 512 → 용량 512 를 넘는다)

에는 쓸 수 없다. 읽기는 PLC 값을 호출자에게 정상으로 돌려주지만, 캐시 쓰기 실패(`-ERANGE`)를 **조용히 버린다**
(로그 없음). 이 때문에 A20261011-4 에서 어댑터가 실패를 보고할 때 원인이 드러나지 않는다.
`docs/protocols/slmp.md` 부록 D-5 는 "클라이언트는 … 로컬 캐시는 자기 일관적" 이라고, 7.2 절(:1046)은 맵 크기가
"서버 시뮬에서 D4096 이상은 C056h" 에만 영향을 준다고 적고 있어 이 동작과 맞지 않는다. 같은 문서 5.8 절의 예제 `ZR100000` 은
기본 설정의 클라이언트로 쓸 수 없다.

**근거 (파일:줄, 기준 커밋 `8dd315b`):**
- `stacks/slmp/src/slmp_stack.c:920-937` `slmp_stack_client_batch_write` — "Always update local cache". `slmp_stack_write_bits`/
  `slmp_stack_write_bytes` 가 실패하면 `:938` 의 역할 확인과 `:944` 원격 쓰기 전에 반환.
- `stacks/slmp/src/slmp_stack.c:367-369` (`head + quantity > slot->capacity` → `-ERANGE`), `:412-415` (비트).
- `stacks/slmp/src/slmp_stack.c:894-895`, `:909-910` `slmp_stack_client_batch_read` — 캐시 쓰기 반환값을 무시하고 0.
- `stacks/slmp/src/slmp_stack.c:198-229` 맵 용량 (`SLMP_DEV_WORDS_DEFAULT` 4096, `SLMP_DEV_BITS_DEFAULT` 8192, `slmp_types.h:48-49`).

**재현 (수정 전, `slmp_oracle_client` + 사양 기반 가짜 PLC):** 가짜 PLC 는 0401/0000 에 워드 n = `(0x1000+n) & 0xFFFF`,
0401/0001 에 비트 n = `n % 2` (니블), 1401 은 기록 후 `0000`. `slmp_oracle_client` 에 `--start/--dev/--bit/--write` 옵션을
추가했다 (이 감사의 자체 PR, 기본값은 예전 동작).

```
--start 4095 --write 1234                 → WRITE 4095 0     | 1401: [(sub 0000, head 4095, dev A8, 1, '3412')]   (대조군)
--start 100 --dev 90 --bit --write 1      → WRITE 100 0      | 1401: [(sub 0001, head 100, dev 90, 1, '10')]      (대조군)
--start 5001 --write 1234                 → WRITE 5001 -34   | 1401: []
--start 512 --dev 90 --write 1234         → WRITE 512 -34    | 1401: []
--start 8192 --dev 90 --bit --write 1     → WRITE 8192 -34   | 1401: []
--start 5000                              → READ 5000 0 2388  (읽기는 정상: 0x1000+5000)
--start 512 --dev 90                      → READ 512 0 1200
```

오라클 `test_client_stack_writes_high_device_numbers[D5001-word|M512-word|M8193-bit]` 를 `--runxfail --tb=line` 으로 돌린 결과:

```
test_slmp_oracle.py:456: AssertionError: (['WRITE', '5001', '-34'], [])
test_slmp_oracle.py:456: AssertionError: (['WRITE', '512', '-34'], [])
test_slmp_oracle.py:456: AssertionError: (['WRITE', '8193', '-34'], [])
```

**기대값과 출처:**
- 3E 프레임, Q 호환 서브커맨드 `0000`/`0001` 의 선두 디바이스 번호는 3바이트(0~0xFFFFFF), 디바이스 코드 1바이트
  (사양 요청 형식. pymcprotocol 0.3.0 `_make_devicedata` 도 `devicenum.to_bytes(3, "little")`). 디바이스 범위 검사는
  PLC 가 하고, 범위 밖이면 PLC 가 엔드 코드(`C056h` 등)로 답한다.
- MELSEC Q 기본 파라미터 디바이스 점수 D 12288, W 8192(W0~W1FFF), M 8192 (확신 높음, 기종 매뉴얼로 재확인 가능).
  D5001·M512·M8193 은 정상 주소이고, M8193 처럼 PLC 범위를 넘을 수 있는 주소도 판단은 PLC 의 엔드 코드로 해야 한다.
- 기대 1401 바이트 배치는 pymcprotocol `batchwrite_wordunits`/`batchwrite_bitunits` 와 같다 (워드 LE, 비트 앞 점 상위 니블).

**수정 범위:** `stacks/slmp/`, `tests/` (+ 오라클 DUT `tests/oracle/dut/slmp_oracle_client.c` 옵션은 이 감사의 오라클 PR 에 포함).
- 클라이언트 역할의 `slmp_stack_client_batch_write`/`_read` 는 캐시 용량과 무관하게 원격 요청을 보내고 결과를 돌려준다.
  캐시 갱신 실패는 결과를 바꾸지 않고 `LOG_WARN` (한 번만 또는 rate limit) 으로 남긴다. 캐시를 없애거나 sparse 로 바꾸는 것도 허용.
- 서버 역할(시뮬)의 동작은 그대로 (맵 밖 → `C056`).
- 스택 단위 테스트에 세 경우(워드 4096 이상, 비트 8192 이상, 비트 디바이스 워드 단위 512 이상) 추가.

**완료 조건:**
- 오라클 `test_client_stack_writes_high_device_numbers` 3개가 통과하고 `@known_defect("A20261011-3", …)` 표시를 지운다.
- 대조군 `test_client_stack_reads_high_device_numbers` 4개와 같은 파일의 다른 결과가 그대로다.
  A20261011-4 테스트 4개는 **xfail 그대로** (어댑터가 여전히 맵을 거치므로).
- 스크래치 검증: `client_batch_write` 의 캐시 실패를 클라이언트 역할에서 무시하는 최소 패치에서 이 3개만 XPASS(strict)였고,
  A20261011-4·-5 와 기존 T10 테스트는 xfail 그대로였다.

## A20261011-4. 클라이언트 어댑터가 로컬 맵 밖 주소의 포인트를 읽지도 쓰지도 못한다

**문제:** 클라이언트 모드의 어댑터는 PLC 에서 읽은 값을 스택 로컬 맵에 넣은 뒤 **맵에서 다시 읽어** 앱에 준다. 쓰기도 맵에 먼저
쓴 뒤 맵에서 창을 읽어 보낸다. A20261011-3 과 같은 범위의 주소에서

- `access: "write"`/`"readwrite"` 포인트: PLC 가 정상 응답했는데 `fb_read_*` 가 `FB_ERR_IO`(-3). poll 은 경고 없이 성공
  (`POLL 0`), `health()` 의 last_error 도 비어 있어 원인을 찾을 수 없다.
- `access: "read"`/`"readwrite"` 포인트: `fb_write_*` 가 `FB_ERR_IO` 이고 PLC 로 1401 이 나가지 않는다.

D5000·W1000·ZR100000 은 흔한 정상 주소라서, 기본 설정(`map_words`/`map_bits` 미지정)의 현장 설정이 조용히 동작하지 않는다.
`map_words` 를 키우면 피할 수 있지만 문서(`docs/slmp_stack.md` 6.1 절, slmp.md 9장 표)는 이 필드를 "서버/캐시 용량" 으로만 설명한다.

**근거 (파일:줄, 기준 커밋 `8dd315b`):**
- `adapters/slmp/slmp_adapter.c:816-827` `slmp_read_point` — `remote_sync_read` (결과 창을 버림, `:687-697`) 뒤 `read_map_window` 가
  맵에서 다시 읽음 → `slmp_stack_read_bytes`/`_read_bits` 의 `-ERANGE` (`slmp_stack.c:346-348`, `:387-390`).
- `adapters/slmp/slmp_adapter.c:940-943` `slmp_write_point` — `write_map_window` 실패 시 원격 쓰기 전에 반환.
  `:668-685` `remote_sync_write` 도 맵에서 창을 읽어 보낸다.
- `adapters/slmp/slmp_adapter.c:715-720` `slmp_poll_cycle` — 스택이 0 을 돌려주므로 경고 없음 (A20261011-3 의 `slmp_stack.c:909`).
- `core/fb_api.c:108-134` `map_errno` — `-ERANGE` → `FB_ERR_IO`.

**재현 (수정 전, `mb_slmp_oracle_app` 클라이언트 설정 + 같은 가짜 PLC):** `timeout_ms` 300 (감시 타이머 때문에 4000 으로 올라감),
uint16 포인트.

```
> START -> START 0
> POLL -> POLL 0 1.1            (가짜 PLC 가 0401 을 포인트마다 받음: D4095, D5000, W 0x1000, ZR100000, M512, M496)
> RU32 d_ok      (D4095)          -> R 0 8191      (대조군)
> RU32 d_hi      (D5000)          -> R -3 0
> RU32 w_hi      (W "1000")       -> R -3 0
> RU32 zr        (ZR100000)       -> R -3 0
> RU32 m_word    (M512 워드)      -> R -3 0
> RU32 m_word_ok (M496 워드)      -> R 0 4592      (대조군)
> WU32 out_ok 0x1234 (D4094)      -> W 0           1401 수신: head 4094 data 34 12
> WU32 out_hi 0x1234 (D5001)      -> W -3          1401 수신 없음
stderr: slmp WARN/ERROR 줄 없음 (timeout_ms 경고 1줄만)
```

같은 가짜 PLC 에 pymcprotocol 0.3.0 (`Type3E("Q")`) 으로 읽으면 `D5000 → [9096]`, `W1000 → [8192]`, `ZR186A0`(= 100000) → `[-26976]`
(= 38560), `M512 → [4608]`. 요청 바이트는 감시 타이머 값만 다르고 DUT 와 같다 (head·디바이스 코드·점수).

오라클 `test_adapter_client_reads_high_device_numbers[D5000|W1000|M512-word]`,
`test_adapter_client_writes_high_device_number` 를 `--runxfail --tb=line` 으로 돌린 결과:

```
test_slmp_oracle.py:516: AssertionError: assert ['R', '-3', '0'] == ['R', '0', '8192']
test_slmp_oracle.py:516: AssertionError: assert ['R', '-3', '0'] == ['R', '0', '4608']
```

**기대값과 출처:**
- A20261011-3 과 같다 (3바이트 선두 번호, MELSEC 기본 디바이스 점수, 범위 판단은 PLC 엔드 코드). W·ZR 의 번호 기수는
  저장소 규칙(W 16진, ZR 10진)을 따랐다. ZR 기수 자체는 T10-7 (pymcprotocol 은 16진이라 `ZR186A0` 으로 같은 번호를 읽었다).

  `--start 100000 --dev B0` 는 선두 번호를 정수로 직접 넘기므로 기수와 무관하다.
- 기대 값은 가짜 PLC 의 규칙(`0x1000 + n`)과 pymcprotocol 이 같은 PLC 에서 읽은 값이 같다.

**수정 범위:** `adapters/slmp/`, `tests/`. **A20261011-3 이후.**
- 클라이언트 모드에서 PLC→앱 포인트는 `slmp_stack_client_batch_read` 가 돌려준 창(`raw_out`)에서 바로 디코드한다
  (비트 필드 포인트 포함). 앱→PLC 쓰기는 앱 값으로 만든 창을 그대로 `slmp_stack_client_batch_write` 에 넘긴다.
  비트 필드 RMW 는 원격 읽기 창을 기준으로 한다. 맵은 쓰지 않거나 실패를 무시한다.
- 다른 동작(맵 안 주소, 서버 모드, `readwrite` 의 매 읽기 원격 동기화)은 그대로.
- `tests/test_slmp_adapter.c` 에 클라이언트 모드 경계 테스트 추가.

**완료 조건:**
- 오라클 `test_adapter_client_reads_high_device_numbers` 3개와 `test_adapter_client_writes_high_device_number` 가 통과하고
  `@known_defect("A20261011-4", …)` 표시를 지운다. (쓰기 테스트는 A20261011-3 이 먼저 병합돼야 통과한다.)
- 대조군 `test_adapter_client_low_device_numbers` 와 기존 어댑터 테스트(T10-3·T10-4 xfail 포함) 결과가 그대로다.
- 스크래치 검증: 위 방식의 최소 어댑터 패치만 넣으면 읽기 4개만 XPASS(strict), 쓰기 1개는 xfail 그대로였다.
  A20261011-3 최소 패치와 함께 넣으면 -3 의 3개와 -4 의 5개(당시 ZR 포함)가 XPASS 였고, A20261011-5·T10 테스트는 xfail 그대로였다.

## A20261011-5. 서버 시뮬이 비트 단위 일괄 읽기·쓰기를 7168 점까지 받지 않는다

**문제:** 서버(랩 시뮬)는 비트 단위 점수를 `1 ≤ qty ≤ 7168` 로 검사하지만 (`SLMP_QTY_BIT_MAX`), 버퍼가 작아서

- 비트 단위 읽기 3841~7168 점은 `C051` (점수 오류) 로 거부한다. 응답 데이터 ⌈n/2⌉ 바이트가 `SLMP_PAYLOAD_MAX` 1920 을 넘기 때문이다.
- 비트 단위 쓰기 4055~7168 점은 요청 프레임이 `SLMP_FRAME_MAX` 2048 을 넘어 **응답 없이 연결을 끊는다** (RST).

T10-1 (니블 포장) 이전 문서는 "비트 읽기는 사실상 1920 점까지" 라고 적었다 (slmp.md:1042, 지금은 3840). 단위 테스트는 7169 거부만
보고 7168 수락은 보지 않는다 (`tests/test_slmp_stack.c:359-368`).

**근거 (파일:줄, 기준 커밋 `8dd315b`):**
- `stacks/slmp/include/slmp_types.h:35` `SLMP_FRAME_MAX 2048`, `:37` `SLMP_PAYLOAD_MAX 1920`, `:39-41` "bit 1–7168".
- `stacks/slmp/src/slmp_stack.c:1023-1027` 점수 검사(7168 통과), `:1033-1038` `wire > sizeof(payload)` → `C051`.
- `stacks/slmp/src/slmp_stack.c:1314-1320` `serve_client` — `need > SLMP_FRAME_MAX` 면 `slmp_close_client` (응답 없음).
  `:1324` 응답 버퍼도 `SLMP_FRAME_MAX` 라 7168 점 읽기 응답(11+3584 = 3595 B)이 들어가지 않는다.

**재현 (수정 전, `slmp_oracle_server` + raw 소켓, pymcprotocol):**

```
read 7168 request: 50 00 00 ff ff 03 00 0c 00 10 00 01 04 01 00 00 00 00 90 00 1c
bit read  M0 x3840: hdr=d0 00 00 ff ff 03 00 82 07 end=0x0000 data_bytes=1920     (대조군)
bit read  M0 x3841: hdr=d0 00 00 ff ff 03 00 02 00 end=0xC051 data_bytes=0
bit read  M0 x7168: hdr=d0 00 00 ff ff 03 00 02 00 end=0xC051 data_bytes=0
bit write M0 x4054 (frame 2048 B): end=0x0000                                       (대조군)
bit write M0 x4055 (frame 2049 B): no response (ConnectionResetError)
```

**기대값과 출처:**
- SLMP Reference Manual / MC 프로토콜 레퍼런스 매뉴얼: 디바이스 일괄 읽기(0401)·쓰기(1401), Q 호환 서브커맨드의 처리 점수
  워드 단위 1~960 점, 비트 단위 1~7168 점. 저장소도 같은 값을 사양 상한으로 둔다 (`slmp_types.h:39-41`, 7169 → `C051` 테스트).
- 요청 바이트 배치는 pymcprotocol 0.3.0 `Type3E("Q").batchread_bitunits`/`batchwrite_bitunits` 와 같다 (점수 0x1C00, 니블 데이터).
  pymcprotocol 은 수량 상한을 검사하지 않으므로 상한 판정 근거는 사양이다. 쓴 값의 되읽기 판정은 pymcprotocol 로 한다.

**수정 범위:** `stacks/slmp/`, `tests/`.
- 서버 수신 버퍼·응답 버퍼·읽기 페이로드를 최대 프레임(비트 쓰기 요청 9+12+3584 = 3605 B, 비트 읽기 응답 3595 B)에 맞춘다.
  `SLMP_FRAME_MAX`/`SLMP_PAYLOAD_MAX` 는 클라이언트·퍼즈 하니스(`tests/fuzz/fuzz_slmp_request.c`)도 쓰므로 함께 확인한다.
- 단위 테스트에 비트 7168 점 읽기·쓰기 수락을 추가한다 (7169 거부는 기존 테스트).
- `docs/protocols/slmp.md` 7.2 절 `SLMP_PAYLOAD_MAX` 행을 갱신한다 (문서 항목 A20261011-2 와 겹치면 어느 쪽에서 해도 됨).

**완료 조건:**
- 오라클 `test_server_bit_batch_up_to_7168` 4개가 통과하고 `@known_defect("A20261011-5", …)` 표시를 지운다.
- 대조군 `test_server_bit_batch_within_buffer` 2개, 기존 `test_word_batch_read` 등과 `ctest -R slmp -LE soak_ci` 가 그대로 통과한다.

  A20261011-3·-4·T10 테스트는 xfail 그대로였다.

## 확인 필요 (큐에 넣지 않음)

1. **클라이언트 소켓 타임아웃 = 감시 타이머 (같은 값).** `slmp_stack_create` 는 `timeout_ms < monitor_ms` 면 `timeout_ms = monitor_ms`
   (`slmp_stack.c:286-295`). 가짜 PLC 가 첫 요청에 엔드 코드 `C0B5` + 에러 정보 9 B 로 늦게 답하면 (`slmp_oracle_client --count 2`,
   감시 타이머 기본 4 s):

   ```
   delay 3.9s: READ 1 -5 0000 | READ 2 0 1002    | accepts 1   (엔드 코드 받음)
   delay 4.1s: READ 1 -110 0000 | READ 2 -11 0000 | accepts 1  ("closed client socket after error -110; reconnect in 100 ms")
   delay 4.5s: 위와 같음
   ```

   감시 타이머 만료 직후 PLC 가 보내는 이상 응답을 못 받고 `-ETIMEDOUT` + 연결 폐기 + 백오프(다음 요청 `-EAGAIN`)가 된다.
   pymcprotocol 은 "socket timeout is always set timer+1sec. To recieve Timeout answer" (`type3e.py:80-82`, `setaccessopt`) 로
   여유를 두고, 저장소 주석(`:284-285`)도 같은 의도다. 하지만 사양이 클라이언트 대기 시간을 정하지 않고, 여유를 늘리면 T3(블로킹)과
   상충하며, 자국 CPU 직결 접속에서는 감시 타이머 만료가 거의 없다. 여유 폭은 사람이 정한 뒤 `stacks/slmp/` 항목으로 넣을 수 있다.
2. **서버의 요구 데이터 길이 불일치.** 일괄 쓰기 본문이 점수보다 길면 남는 바이트를 무시하고 `0000` (`slmp_stack.c:1067-1071` 는 부족만 검사),
   12바이트 미만 읽기 요청은 무응답 폐기 (`:997-999`). 사양 엔드 코드 `C061h` 로 보이나 사양서 표로 확인하지 못했다. T10-5
   (엔드 코드·에러 정보·쓰기 길이 부족 무응답) 의 완료 조건에 두 경우를 더하는 것을 권한다. slmp.md:1001-1002 가 일부 서술.
3. **클라이언트가 요청보다 긴 읽기 응답을 받는다.** `dlen < need` 만 거부 (`slmp_stack.c:884`, `:899`). 앞부분만 쓰므로 미러 손상은 없다
   (Modbus A20261004-2 와 다름). pymcprotocol 도 응답 길이를 보지 않아 독립 근거가 없다. 응답 에코 미검증(D-12)과 함께 "프레임 이상은
   연결 폐기" (slmp.md 7.1) 정책을 정할 때 판단. 짧은 응답의 `-ENOSPC` 가 `FB_ERR_NOSPC`("caller buffer too small")로 보이는 점도 같이.
4. **비트 단위 bool `bit_count` > 1** (`slmp_adapter.c:397-402`, `:774-777`, `:733-739`): 앱 바이트를 점마다 1바이트로 복사한다.
   Modbus 감사 "확인 필요 3" 과 같은 유형, 의미가 문서에 없다.
5. **서버가 워드 디바이스의 비트 단위 접근(D + `0001`)을 받는다**, **네트워크 번호·PC 번호·요구처 모듈 I/O 를 검사하지 않는다**
   (`slmp_stack.c:993-1089`). 실 PLC 의 엔드 코드를 확신하지 못한다.
6. **`json_get_int` 가 문자열 값을 base 0 으로 파싱** (`slmp_adapter.c:83`): `"offset":"010"`·`"quantity":"010"`·`"port":"0502"` 가 8진.
   주소 문자열(`parse_device_head`)은 10/16진이라 같은 어댑터 안에서도 다르다. Modbus T9-3 과 같은 유형이지만 SLMP 주소 자체는 영향 없음.
7. **`bit` ≥ 64 시프트 UB** (`slmp_codec.c:505-508`, `:520-523`), 비트 필드가 4워드를 넘으면 잘림 (`slmp_adapter.c:582`, `:619`). 설정 검증 문제. 퍼즈 라운드 대상.
8. **iQ-R 서브커맨드 0002/0003** (pymcprotocol `plctype="iQ-R"`) → 서버 `C050`. 제품 범위가 Q 호환이라 비목표일 수 있다 (T10-5 의 `C059` 와 함께 정리).

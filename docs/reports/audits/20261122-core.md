## A20261122-1. 64비트 정수 포인트(uint64/int64)를 읽고 쓰면 값이 바뀐다 (double 경유, `llround` 범위 밖)

**문제:** 코어의 숫자 변환은 읽기·쓰기 모두 `double` 을 거친다. `double` 가수는 53비트라 2^53 보다 큰 64비트 정수는 반올림된다.
`INT64_MAX`·`UINT64_MAX` 근처 값은 `llround` 의 반환 범위(long long)를 넘어 결과가 정해지지 않는다 (x86-64 glibc 에서는 `LLONG_MIN`, `FE_INVALID`).
그래서 native 타입이 `FB_TYPE_U64`/`FB_TYPE_I64` 인 포인트를 같은 타입으로 읽고 써도 앱이 받는 값과 PLC 로 나가는 값이 와이어 값과 다르다.
호출은 모두 `FB_OK` 라 앱은 알 수 없다. 예: `INT64_MAX` 를 쓰면 `INT64_MIN` (`80 00 … 00`) 이 나간다. 결함이 코어에 있어 64비트 정수를 쓰는 어댑터가 모두 같은 경로를 탄다.

**근거 (파일:줄, 기준 커밋 `b0cff99`):**
- `core/fb_api.c:567-615` `decode_numeric` — 출력이 `double *out`. `:608` `be_load_uint` 로 정확한 `uint64_t` 를 읽고 `:609-613` 에서 `(double)` 로 바꾼다.
- `core/fb_api.c:686-722` `store_numeric` — `:706` `(int64_t)llround(x)`, `:713` `(uint64_t)llround(x)`.
- `core/fb_api.c:657-684` `value_as_double` — `:669-674` I64/U64 입력을 `(double)` 로.
- `core/fb_api.c:617-655` `encode_numeric` — `:648` `(uint64_t)(int64_t)llround(eng)`, `:651` `(uint64_t)llround(r)`.
- 계약: `include/fb_api.h:57-68` 의 `FB_TYPE_I64`/`FB_TYPE_U64`, `native_type_of` (`core/fb_api.c:259`, `:262`) 가 이 타입을 보고. C11 7.12.9.7 (llround 범위 밖 결과는 unspecified).

**재현 (수정 전):** Modbus 서버 설정에 uint64 포인트(holding 40100)·int64 포인트(holding 40110). 대조로 원시 바이트는 `fb_write_bytes`→`fb_read_bytes` 로 정확히 왕복한다 (어댑터는 값을 바꾸지 않는다).
```
control read_bytes bytes(8): 01 23 45 67 89 AB CD EF
read u64 AUTO rc=0 type=5 value=0x0123456789ABCDF0 (wire 0x0123456789ABCDEF)
read u64 U64 rc=0 value=9223372036854775808 (wire 18446744073709551615)
read i64 AUTO rc=0 type=4 value=-9223372036854775808 (wire 9223372036854775807)
write u64 0x0123456789ABCDEF rc=0 -> wire bytes(8): 01 23 45 67 89 AB CD F0
FE_INVALID raised by write(UINT64_MAX): yes
write u64 UINT64_MAX rc=0 -> wire bytes(8): 80 00 00 00 00 00 00 00
write i64 INT64_MAX rc=0 -> wire bytes(8): 80 00 00 00 00 00 00 00
```

**기대값과 출처:** scale 이 없는 정수 포인트를 native 타입으로 읽으면 와이어 값 그대로, 같은 타입으로 쓰면 그 값의 BE 8바이트. 기준값은 하니스가 넣은 바이트, 손실 규칙은 C11.

**수정 범위:** `core/`, `tests/`.
- scale 이 없는 정수 kind 는 `uint64_t`/`int64_t` 로 디코드·인코드한다. `double` 은 F32/F64 포인트, scale 포인트, F32/F64 요청 타입에만 쓴다. 범위 밖 값에 `llround` 를 부르지 않는다.
- 다른 정수 타입으로 요청해 범위를 벗어나는 경우의 처리는 아래 "확인 필요" 1 과 함께 정한다 (담당자 결정).

**완료 조건:**
- `tests/test_fb_api.c` 의 Modbus 서버 설정에 uint64·int64 포인트를 추가한다. 지금 모두 실패하는 세 검사:
  1. `01..EF` 를 `fb_write_bytes` 하고 AUTO 로 읽으면 `type==FB_TYPE_U64`, `v.u64==0x0123456789ABCDEF`.
  2. `FF…FF` 를 U64 로 읽으면 `UINT64_MAX`, `7F FF…` 를 I64 로 읽으면 `INT64_MAX`.
  3. U64 `0x0123456789ABCDEF`/`UINT64_MAX`, I64 `INT64_MAX`/`INT64_MIN` 을 쓴 뒤 `fb_read_bytes` 가 정확한 BE 8바이트.
- 기존 `test_fb_api` 와 오라클 결과가 그대로다.

## A20261122-2. 코어 포인트 메타가 256개 초과·63자 초과 이름을 말없이 버리거나 잘라, 설정한 포인트를 앱이 못 쓴다

**문제:** `parse_points_meta` 는 포인트를 최대 256개까지만 담고 나머지는 로그 없이 건너뛴다. 이름은 64바이트 버퍼에 잘라 넣는다.
EtherNet/IP 어댑터는 포인트 수 제한이 없고(`realloc`) 이름을 127자까지 받으므로, 스키마상 유효한 설정에서:
1. 257번째 이후 포인트를 읽고 쓰면 `FB_ERR_NOENT`, `fb_list_points` 총수는 256.
2. 64자 이상 이름 포인트는 쓸 수 있는 이름이 없다 (목록의 63자 이름 → `FB_ERR_IO`, 설정 원래 이름 → `FB_ERR_INVAL`).

`fb_open` 은 `FB_OK` 이고 코어 로그는 없다.

**근거 (파일:줄, 기준 커밋 `b0cff99`):**

- `adapters/ethernetip/ethernetip_adapter.c:20` `EIP_ADAPTER_NAME_MAX 128`, `:78-96` `ensure_point_cap` 동적 확장.
- 계약: `include/fb_api.h:185-189` (`fb_list_points` "*out_count is still the total"), `:40` (NOENT = unknown point name), `config/config.schema.json:28-30` (이름 길이·개수 제한 없음), `CLAUDE.md` (실패 원인은 `LOG_ERROR`/`LOG_WARN`).

**재현 (수정 전):** EIP mock 서버 설정, assembly 150 에 uint8 포인트 `p000`~`p299` 와 80자 이름 포인트 1개.

fb_write_u32(p010)=0 (ok)
fb_write_u32(p299)=-2 (point not found)

**기대값과 출처:** `fb_open` 이 성공했다면 설정한 모든 포인트가 목록 총수에 들고 이름으로 읽고 쓸 수 있어야 한다 (`fb_api.h:185-189`, `:40`). 담을 수 없으면 `FB_ERR_CONFIG` + `LOG_ERROR` 로 실패해야 한다.

**수정 범위:** `core/`, `tests/`.
- 63자 초과 이름: `fb_point_info_t.name[64]` 가 ABI 로 고정이므로 `FB_ERR_CONFIG` + `LOG_ERROR` 로 거절.
- 256개 초과: (a) 코어 메타를 동적 배열로, 또는 (b) `FB_ERR_CONFIG` 로 거절. (b) 는 지금 Modbus/SLMP 가 256 초과분을 WARN 후 버리고 여는 설정을 못 열게 한다. **담당자 결정 필요.**

**완료 조건:**

## A20261122-3. Modbus 서버 bind 실패 시 `fb_open`/`fb_reload` 가 `FB_ERR_PERM` 을 돌려준다

**문제:** Modbus 스택은 bind 실패에 `-1` 을 돌려주는데 `-1` 은 `-EPERM` 과 값이 같다. 코어 `map_errno` 를 거쳐 `FB_ERR_PERM` ("permission denied") 이 된다.
`session_connect` 는 INVAL 만 IO 로 바꾸고 나머지는 그대로 넘긴다. 계약에서 PERM 은 "앱 읽기 전용 포인트에 씀" 이고 connect 실패는 IO 다.
포트가 이미 쓰이는 흔한 상황에서 사용자는 권한 문제로 오진한다. 같은 상황에서 SLMP 는 `-98` 을 돌려줘 `FB_ERR_IO` 로 맞게 나온다.

**근거 (파일:줄, 기준 커밋 `b0cff99`):**
- `core/fb_api.c:443-455` `session_connect` `:452` `return map_errno(rc) == FB_ERR_INVAL ? FB_ERR_IO : map_errno(rc);`, `:139` `-EPERM` → PERM. `fb_open` `:1039`, `fb_reload` `:1110` 가 그대로 반환.
- 원인: `stacks/modbus/src/mb_stack.c` `bind` 실패 `return -1;` (`:528-531`), `adapters/modbus/modbus_adapter.c:551-560` 이 그대로 전달.
- 계약: `include/fb_api.h:41` (IO = "adapter/stack I/O or connect"), `:43` (PERM = "write to an app-read-only point"), `docs/app_api.md:67`, `:69`.

**재현 (수정 전):** 127.0.0.1:15712 를 다른 소켓이 listen 하는 상태에서 Modbus·SLMP 서버를 열고, 정상 세션을 그 포트 설정으로 reload.
```
[ERROR][modbus] stack start failed (-1)
[ERROR][slmp] listen failed (-98)
modbus fb_open(busy port) rc=-5 (permission denied)
slmp   fb_open(busy port) rc=-3 (i/o error)
modbus fb_reload(busy port) rc=-5 (permission denied)
```
reload 실패 뒤 옛 세션 복구는 계약대로 된다 (`connected=1 gen=1`, 옛 포트로 접속).

**기대값과 출처:** `FB_ERR_IO` (`fb_api.h:41`, `app_api.md:67`). 같은 조건의 SLMP 결과도 IO.

**수정 범위:** `core/`, `tests/`. `session_connect` 가 connect 실패 코드를 정규화한다 (ENOMEM → NOMEM, ENOSYS/ENOTSUP → UNSUPPORTED, 나머지 IO). Modbus 스택을 `-errno` 로 고치는 것은 별도 항목으로 할 수 있으나 앱 계약을 지키는 곳은 코어다.

**완료 조건:** 포트를 미리 listen 해 둔 상태의 `fb_open` 이 `FB_ERR_IO` (지금 PERM). 정상 세션에서 같은 설정으로 `fb_reload` 하면 `FB_ERR_IO`, generation 그대로, 옛 포트로 접속.

## A20261122-4. `fb_reload` 가 락을 푼 뒤 `rt->generation`·`rt->session` 을 읽어 로그한다 (TSan 데이터 레이스)

      1 core/fb_api.c:1126 in fb_reload
      1 core/fb_api.c:870 in run_cycle_loop      ← thread_stop, A20261008-1 이라 제외

## A20261122-5. `cycle_ms` 가 스키마(정수, 최소 1)를 어겨도 `fb_open` 이 성공하고, `fb_health.cycle_ms` 가 실제 주기와 다르다

**문제:** `config_load` 는 `cycle_ms` 가 숫자이기만 하면 `valueint` 를 검사·로그 없이 받는다.
0·음수면 루프는 8ms 를 쓰지만 `fb_health` 와 open 로그는 원값을 보고한다. 소수는 버림(0.5 → 0 → 실제 8ms, 2.9 → 2ms), 문자열 `"20"` 은 무시되고 8ms.

**근거 (파일:줄, 기준 커밋 `b0cff99`):** `core/config_loader.c:79-82` (검사 없이 `valueint`, 숫자가 아니면 말없이 기본값), `core/fb_api.c:884-887` (`cycle_ms <= 0` 이면 8), `:1498` (`fb_health` 가 원값 보고). 계약 `config/config.schema.json:19` `{"type":"integer","minimum":1,"default":8}`, CLAUDE.md 로그 규칙.

**재현 (수정 전):** 테스트 훅 `fb_test_set_extra_wake_us(900000)` 로 마감 놓침 로그를 일부러 내고, 그 `cycle=` 값으로 루프의 실제 주기를 본다.
```
cycle_ms=0    -> fb_open rc=0, fb_health.cycle_ms=0,  ... cycle=8000us
cycle_ms=-5   -> fb_open rc=0, fb_health.cycle_ms=-5, ... cycle=8000us
cycle_ms=0.5  -> fb_open rc=0, fb_health.cycle_ms=0,  ... cycle=8000us
cycle_ms="20" -> fb_open rc=0, fb_health.cycle_ms=8,  ... cycle=8000us
cycle_ms=2.9  -> fb_open rc=0, fb_health.cycle_ms=2,  ... cycle=2000us
```

**기대값과 출처:** 스키마를 어기면 `config_load` 실패 → `fb_open`/`fb_reload` 가 `FB_ERR_CONFIG` 와 `LOG_ERROR("config")`. 적어도 `fb_health.cycle_ms` 는 루프가 실제 쓰는 값.

**수정 범위:** `core/`, `tests/`. `cycle_ms` 가 있으면 정수(소수부 0)이고 1 이상인지 검사, 숫자가 아니면 거절. 거절 대신 경고 후 8 로 두고 health 에도 8 을 보고하는 방식도 있다 — **담당자 결정 필요**. 상한도 같이 정하면 좋다 (확인 필요 2).

**완료 조건:** `cycle_ms` 0, -5, 0.5, `"20"` 을 각각 열어 모두 `FB_ERR_CONFIG` 와 `[ERROR][config]` 한 줄 (지금 `FB_OK`). 클램프 방식을 고르면 `FB_OK`, health 8, `[WARN][config]` 한 줄. 유효 값과 기존 테스트 결과는 그대로.

## 확인 필요 (큐에 넣지 않음)

1. **좁은 정수 포인트에 범위 밖 값 쓰기.** 쓰기는 감김과 클램프가 섞여 있고 (`write_u32(u16,70000)` → 4464, `write_i32(u16,-1)` → 0, `write_i32(i16,40000)` → -25536), 읽기는 `read_u32(i16=-5)` → `FB_ERR_TYPE` 로 에러다 (`core/fb_api.c:640-653`, `:698-700`). 계약 근거가 없어 결함으로 올리지 않는다. A20261122-1 수정 때 담당자가 규칙을 정하면 좋다.
2. **고정 주기 모드에서 `fb_stop`/`fb_close`/데몬 종료가 최대 `cycle_ms` 까지 늦는다.** `clock_nanosleep` 은 `thread_stop` 으로 깨지 않고, SIGINT/SIGTERM 은 EINTR 뒤 다시 잔다 (`:936-938`). `cycle_ms=3000` 에서 `fb_stop took 2.90 s`. `cycle_ms` 가 1e10 이면 `valueint` 가 INT_MAX 로 포화되어 약 24.8일을 잔다. 공개 계약에 종료 지연 상한이 없다. 큐 74 의 깨우기 파이프도 이벤트 모드만 다룬다.
3. **지터 1초 창(`jitter_window_*`) 상태가 `fb_stop`→`fb_start` 를 건너 남는다** (`:812-846`). 재시작 첫 사이클에 오래된 횟수로 요약이 찍힐 수 있다. 코드만 읽었고 재현하지 않았다.
4. **`fb_run` 이 `thread_on` 을 락 없이 읽는다** (`:1555`). 문서가 `fb_start` 와의 동시 사용을 금지하므로 결함으로 보지 않는다.
5. **어댑터가 `FB_WIRE_CAP`(1024) 보다 긴 값을 돌려주면 `adapter_read_copy` 가 잘라서 `FB_OK`** (`:537-541`). STRING/BYTES 인데 `FB_ERR_NOSPC` 가 아니다. 현재 어댑터로는 재현 경로가 없다.

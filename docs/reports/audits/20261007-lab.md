## A20261007-2. PN 장치가 인터페이스 MAC 대신 고정 기본값 `02:FB:00:00:00:01` 을 쓴다

**문제:** 실제 인터페이스에서 돌 때도 DCP·LLDP·RTC1·Connect 응답(CMResponderMacAdd)에 고정 MAC `02:FB:00:00:00:01` 을 쓴다.
같은 장치의 IP(ARP) 트래픽은 인터페이스 MAC 을 쓰므로, 한 장치가 두 MAC 을 쓴다. 컨트롤러는 DCP Identify 로 배운 MAC
(`02:FB:…`)으로 O→T RTC1 을 보내는데, 실 NIC 은 자기 MAC 이 아닌 유니캐스트를 하드웨어에서 버리므로(무차별 모드를 켜지 않는다)
O→T 를 못 받아 data-hold 만료로 AR 이 끊긴다. 같은 기본값을 쓰는 장치 두 대는 MAC 이 충돌한다. veth 는 MAC 필터가 없어서
이 랩에서는 AR 이 유지되지만, 인터페이스 MAC 으로 보낸 O→T 는 장치가 버린다 (아래 재현 2).

**근거 (파일:줄, 기준 커밋 `811b1dd`):**
- `stacks/profinet/src/pn_stack.c:66-75` `pn_stack_create` — `cfg.mac_set` 이 0 이면 `02:FB:00:00:00:01` 을 넣고 **`mac_set = 1`** 로 만든다.
- `stacks/profinet/src/pn_eth.c:102-106` `pn_eth_open` — `!mac_set` 일 때만 `SIOCGIFHWADDR` 로 인터페이스 MAC 을 읽는다.
  `pn_stack_start` 는 create 뒤에 불리므로 이 분기에 도달하지 않는다 (의도한 경로가 죽어 있다).
- `stacks/profinet/src/pn_stack.c:162` — 수신 프레임은 `dst == cfg.mac` 일 때만 장치 앞으로 본다.
- `adapters/profinet/` 는 MAC 을 설정하지 않는다 (`grep mac` 없음) → 제품 경로도 같다.
- 입문서 `docs/protocols/profinet.md:105-108`, `:215` 는 이 값을 "스택 기본값" 으로만 적었다.

**재현 (`tests/oracle/test_pn_lab.py`, `pn_oracle_lab` + scapy, veth):**
1. DCP Identify 응답과 RTC1 의 출발지가 `02:fb:00:00:00:01`, 인터페이스 MAC 은 다르다:
   ```
   test_pn_lab.py:183: AssertionError: DCP 출발지 02:fb:00:00:00:01 / 인터페이스 2e:7a:cf:47:dc:41
   ```
2. O→T 를 인터페이스 MAC 으로 보내면 장치가 받지 않아 `AR aborted: RT data-hold timer expired` (탐색 실행).
   DCP 로 배운 `02:fb:…` 로 보내면 유지된다.

**기대값과 출처:** 장치 MAC = 그 인터페이스의 MAC (DCP 응답 출발지, RTC1 출발지, ARBlockRes CMResponderMacAdd, LLDP Chassis/Port 가 모두 같은 값).
- p-net `src/common/pf_eth.c` (`pf_eth_init_netif`) 는 `pnal_get_macaddress(netif_name, &pnal_mac_addr)` 로 인터페이스 MAC 을 읽어 쓴다.
- IEEE 802.3: 송신 프레임의 출발지 주소는 그 스테이션의 주소이고, NIC 은 자기 주소·브로드캐스트·가입한 멀티캐스트가 아닌 유니캐스트를 받지 않는다.
- 저장소 자신의 `pn_eth_open` 도 인터페이스 MAC 을 읽으려 한다 (의도는 같고 순서가 틀렸다).

**수정 범위:** `stacks/profinet/`, `tests/`.
- 실제 인터페이스를 쓸 때는 인터페이스 MAC 을 쓴다. 기본값은 mock(인터페이스 없음)일 때만, 또는 사용자가 MAC 을 지정하지 않았고
  인터페이스 MAC 을 못 읽었을 때만 쓴다. 사용자 지정 MAC(있다면)은 우선한다.

**완료 조건:**
- 랩 `test_pnlab_device_uses_interface_mac` 가 통과하고 `@known_defect("A20261007-2", …)` 를 지운다 (검증 담당이 랩을 돌려 확인).
- mock 오라클(`test_pn_oracle.py`)과 기존 단위 테스트 결과가 그대로다 (mock 기본 MAC 을 쓰는 테스트 — 예: `tests/test_pn_dcp.c:330` 의 지연 계산 — 는 영향 없음).
- 스크래치 검증: `pn_stack_create` 기본값 블록에서 `mac_set = 1` 만 지운 패치에서 이 테스트만 XPASS(strict) 가 되고,
  랩 나머지 `5 passed, 2 xfailed`, mock PN 오라클 `16 passed, 32 xfailed` 로 그대로였다.

## 실제 경로에서 맞는 것 (회귀 감시)

- PN Connect 를 실제 UDP 34964 로 주고받음 (PNIOStatus 0).
- ApplicationReady(블록 0x0112)가 컨트롤러 IP 의 UDP **34964** 로 온다 — T12-5 (#89) 의 목적지 수정이 실제 소켓 경로에서도 맞다.
- O→T 를 협상 주기로 보내는 동안 AR 유지, RTC1 은 선로 위 60바이트, DataStatus `0x35`.
- 10회 반복 실행이 모두 같은 결과 (`5 passed, 3 xfailed`).

## 확인 필요

- ApplicationReady 에 0x8112 로 답하지 않으면 장치가 1초 간격으로 계속 재전송한다 (PR #89 비차단 메모와 같음).
- veth 에는 NIC 패딩·MAC 필터가 없다. 최소 길이·MAC 필터 영향은 실 NIC 랩에서 다시 봐야 한다.

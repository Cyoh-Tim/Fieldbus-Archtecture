## A20261018-1. O→T 데이터 길이가 연결 크기와 다른 Class 1 패킷을 출력에 부분 적용한다

**문제:** Class 1 O→T 패킷의 Connected Data 길이를 Forward Open 에서 협상한 O→T 연결 크기와 비교하지 않는다. 앞 2바이트를 순번으로 떼고
남은 바이트를 `min(남은 길이, output_size)` 만큼 출력 Assembly 에 복사한다. 그래서 짧은 패킷은 출력 앞부분만 바꾸고(뒤는 이전 값이 남아
서로 다른 주기의 값이 섞인 출력이 된다), 긴 패킷은 잘라서 쓴다. 고정 크기(NCP F/V = 0) 연결에서 크기가 다른 패킷은 잘못된 데이터다.
워치독도 이 패킷으로 갱신된다.

**근거 (파일:줄, 기준 커밋 `9a2abc2`):**
- `stacks/ethernetip/src/eip_io.c:82-112` `eip_io_handle_udp` — `if (dlen >= 2) { data += 2; dlen -= 2; }` 후
  `n = dlen; if (n > s->output_size) n = s->output_size; memcpy(s->output_data, data, n);`. `c->o2t_size` 와 비교하는 곳이 없다.
- `:79-80` — 길이 검사 전에 `o2t_seq`·`last_rx_ns` 를 갱신한다.

**재현 (오라클, 사양 기반 인코더, DUT `eip_oracle_adapter`):** O→T 6(데이터 4 + 순번 2) 으로 연결 후 `AA BB CC DD` 를 보내고,
이어서 데이터 2바이트·8바이트 패킷을 보낸다.

```
after 4B O->T : aabbccdd
after 2B O->T : 1122ccdd      ← 앞 2바이트만 바뀜 (서로 다른 주기 값이 섞임)
after 8B O->T : 55555555      ← 잘라서 적용
```

`test_o2t_wrong_length_not_applied[short|long]` 를 `--runxfail` 로 돌린 결과:
`AssertionError: 길이 2B O→T 가 출력에 적용됨: 1122ccdd`, `AssertionError: 길이 8B O→T 가 출력에 적용됨: 11111111`.

**기대값과 출처:**
- 독립 구현 OpENer (`d8820ef`) `source/src/cip/cipassembly.c:137-153` `NotifyAssemblyConnectedDataReceived` —
  `if(assembly_byte_array->length != data_length) { "wrong amount of data arrived for assembly object"; return kEipStatusError; }`
  (데이터를 복사하지 않는다). 호출부 `cipioconnection.c` `HandleReceivedIoConnectionData` 는 순번(2)·Run/Idle(4)을 뗀 길이로 부른다.
- 독립 구현 EIPScanner `src/IOConnection.cpp:83-86` (소비 쪽 동작) — 고정 크기 연결에서 `ioData.size() != _t2oDataSize` 이면
  "has fixed size … bytes were received. Ignore this data." 로 버린다.
- `docs/protocols/ethernetip.md` 8.1 표: UDP I/O 길이 불일치는 "무응답(버림)" 층이다. 5.6.4 [사양]: 연결 크기 = 데이터 + 순번 2 (+ Run/Idle 4).

**수정 범위:** `stacks/ethernetip/`, `tests/`.
- 고정 크기 연결에서 `payload_len != c->o2t_size` 이면 데이터를 버린다 (출력 이미지 불변). Run/Idle 연결도 같은 길이 기준.
  가변 크기(F/V = 1)를 지원하지 않는다면 그 요청은 FO 에서 거절하거나 `≤ 크기` 규칙을 따로 둔다.
- 워치독 갱신을 길이 검사 뒤로 둘지는 선택 (OpENer 는 길이와 무관하게 갱신). 오라클은 출력만 본다.
- T11-8 (순번 비교) 과 같은 함수를 고치므로 그 PR 과 충돌에 주의. 오라클은 순번을 1→2 로 올려 T11-8 수정과 독립이다.

**완료 조건:** `test_o2t_wrong_length_not_applied[short]`·`[long]` 통과 (`A20261018-1` 표시 삭제), 기존 Class 1 I/O 오라클 그대로 통과.
단위 테스트로 짧은/긴/정확한 길이 3가지와 Run/Idle 연결(데이터+6)의 짧은 패킷을 보인다.

## A20261018-2. Class 1 연결 크기에 2바이트 순번이 빠진 값(= Assembly 크기)도 수락하고, 그 연결의 송수신 크기가 협상과 다르다

**문제:** Forward Open 크기 검사가 O→T `asm`·`asm+2`·`asm+6`, T→O `asm`·`asm+2` 를 받는다. 사양상 Class 1 크기에는 16비트 순번이 항상
들어가므로 `asm` 은 "데이터 asm−2 바이트" 연결이고, 장치 Assembly 와 맞지 않아 거절해야 한다. 수락한 뒤에도 스택은 순번이 있다고 보고
처리한다:
- T→O 크기 8(= input 8) 로 연결하면 T→O Connected Data 를 10바이트(순번 2 + 데이터 8)로 보낸다 — 협상 크기보다 2바이트 크다.
  고정 크기를 검사하는 스캐너(EIPScanner)는 매 패킷을 버리고 연결 타임아웃이 난다.
- O→T 크기 4(= output 4) 로 연결하면 4바이트 패킷의 앞 2바이트를 순번으로 떼고 2바이트만 출력에 쓴다 (`aabb0000`).

**근거 (파일:줄, 기준 커밋 `9a2abc2`):**
- `stacks/ethernetip/src/eip_cm.c:143-159` `o2t_size_ok`/`t2o_size_ok` — `net == asm_sz || net == asm_sz + 2u` (O→T 는 `+6` 추가).
- `stacks/ethernetip/src/eip_io.c:183-188` `eip_io_produce` — `data_len = 2 + s->input_size` 고정 (`c->t2o_size` 무시).
- `stacks/ethernetip/src/eip_io.c:84-87` — O→T 는 항상 2바이트를 순번으로 뗀다.
- CTT 가 이 형식을 고정한다: `tools/ctt/proto/ethernetip/eip_plugin.c:746-751` (`o2t_size`/`t2o_size` 기본값 = Assembly 크기),
  `tests/scenarios/ethernetip/*.yaml` 의 `o2t_size: 8`/`t2o_size: 8`, `tests/test_eip_stack.c` 의 FO 본문(O→T 8, T→O 32).

**재현 (오라클, DUT `eip_oracle_adapter`, input 8 / output 4):**

```
FO(t2o_size=8) reply: d4 00 00 00 …            ← 성공
T->O packet: … b1 00 0a 00 0100 0102030405060708   connected data len=10 (협상 T→O 크기 8)
FO(o2t_size=4) reply: d4 00 00 00 …            ← 성공
output after 4-byte O->T (seq 0001 + AA BB): aabb0000
```

`test_class1_size_without_sequence_count_rejected[o2t|t2o]` `--runxfail`: 두 경우 모두 `AssertionError: d4000000…` (`0 == 1`, 성공 응답).

**기대값과 출처:**
- `docs/protocols/ethernetip.md` 5.6.4 [사양 — 매우 중요]: "Class 1 연결의 크기는 I/O 데이터 + 16비트 시퀀스 카운트(2) + (있다면) Run/Idle(4)".
  12.1 함정 5: "Class 1 크기에서 seq(2)/Run-Idle(4) 누락 → 0x0109".
- OpENer `source/src/cip/cipioconnection.c:153-180` (O→T)·`:249-275` (T→O) — Class 1 이면 `data_size -= 2` (Run/Idle 설정 시 `-= 4`)
  후 Assembly 길이와 다르면 `0x0127` (Invalid O→T connection size) / `0x0128` (T→O) 로 거절한다.
- EIPScanner `src/ConnectionManager.cpp:76-88` — Class 1 이면 NCP 크기에 항상 `+= 2` (Run/Idle 이면 `+= 4`) 를 더해 요청하고,
  `src/IOConnection.cpp:83-86` 은 고정 크기와 다른 T→O 데이터를 버린다.
- 오라클 기존 `test_forward_open_bad_size_error_format` 이 이미 `0x0109` 또는 `0x0128` 을 허용한다. 새 테스트도 같은 허용 범위다.

**수정 범위:** `stacks/ethernetip/`, `tests/`, 그리고 이 동작을 고정한 CTT (`tools/ctt/proto/ethernetip/`, `tests/scenarios/ethernetip/`)·하네스 (`examples/sw_master.py`)
— 큐 규칙 "각 결함 PR 에서 CTT·golden 이 잘못된 동작을 고정하고 있으면 함께 고친다" (work_queue.md 17줄, 이슈 템플릿 5항).
- O→T 는 `asm+2`(modeless)·`asm+6`(Run/Idle), T→O 는 `asm+2` 만 수락. 나머지는 `0x01/0x0127`·`0x0128` (또는 `0x0109`).
- CTT 기본 `o2t_size`/`t2o_size` 를 `+2` 로 바꾸고 시나리오·단위 테스트 FO 본문의 크기를 맞춘다. 바꾼 기대값을 PR 설명에 적는다.
- `examples/sw_master.py` (`cip_forward_open`, sw-master-soak job) 도 Assembly 크기를 그대로 보낸다 (`:759-768`). 같은 PR 에서 `+2` 로 맞춘다 (T11-6 #126 이 이 하네스를 같은 방식으로 고쳤다).

**완료 조건:** `test_class1_size_without_sequence_count_rejected[o2t]`·`[t2o]` 통과 (`A20261018-2` 표시 삭제). 기존 오라클
(`asm+2`, `asm+6` 성공) 그대로. `ctest -LE soak_ci` 전부 통과 (CTT 시나리오 크기 갱신 포함).

## A20261018-3. Forward Open 연결 경로의 위치·config 인스턴스·클래스를 확인하지 않는다

**문제:** Exclusive Owner 경로는 "Assembly 클래스, config 인스턴스(0x24), 소비 connection point(O→T), 생산 connection point(T→O)" 순서다.
스택은 클래스 값을 버리고, 0x24/0x25/0x2C/0x2D 값을 모두 한 목록에 넣은 뒤 output·input 번호가 **어딘가에 있기만 하면** 수락한다.
그래서 다음이 모두 성공한다 (Exclusive Owner 슬롯을 차지한다):
- 소비·생산이 뒤바뀐 경로 `20 04 24 64 2C 96 2C 65` (O→T 를 입력 Assembly 150 으로 요청) — 스택은 여전히 O→T 를 출력 101 에 쓴다.
- 없는 config 인스턴스 `24 63` (99).
- Assembly 가 아닌 클래스 `20 01` (Identity).

**근거 (파일:줄, 기준 커밋 `9a2abc2`):**
- `stacks/ethernetip/src/eip_cm.c:220-263` `parse_fo_path` — `0x20` 은 `i += 1` (값 무시), 인스턴스·connection point 를 역할 구분 없이 `insts[]` 에 쌓는다.
- `:269-297` `fo_path_ok` — `insts[i] == output_assembly` 와 `== input_assembly` 가 각각 한 번이라도 있으면 통과. config 인스턴스·순서 검사 없음.
- `docs/protocols/ethernetip.md:1236-1238` 이 이 동작("순서·역할 구분 없음", "config 인스턴스는 검사하지 않는다")을 기록만 해 두었다.

**재현 (오라클, DUT `eip_oracle_adapter`, config 100 / output 101 / input 150):**

```
FO path swapped (2C 96 2C 65): d4 00 00 00 …  (성공)
FO path cfg 0x63            : d4 00 00 00 …  (성공)
FO path class 01            : d4 00 00 00 …  (성공)
```

`test_forward_open_connection_path_positions_checked[swapped_points|unknown_config_instance|identity_class]` `--runxfail`:
세 경우 모두 `AssertionError: d4000000…` (`0 == 1`).

**기대값과 출처:**
- `docs/protocols/ethernetip.md` 5.6.6: "첫 인스턴스(0x24)는 config, 그 다음 connection point 두 개는 소비(O→T) → 생산(T→O) 순서".
  같은 절의 ⚠: 경로 문제는 `0x01` + `0x0315`/`0x0117` 등.
- OpENer `source/src/cip/cipconnectionmanager.c:1457-1470` — 경로 클래스가 없으면 `0x012F`/`0x0315`; `:1486-1497` — config 인스턴스가
  그 클래스에 없으면 `0x0315` ("according to the test tool"); `:1553-1612` — 양방향 연결이면 첫 connection point 를 consumed, 둘째를 produced 로 위치로 해석 (`paths_to_encode[0] = consumed_path`).
  `source/src/cip/appcontype.c:178-200` `GetExclusiveOwnerConnection` — `output == consumed && input == produced && config == configuration` 일 때만
  Exclusive Owner, 아니면 Input Only/Listen Only 를 거쳐 `0x012F` (Inconsistent application path combination).
- 저장소 EDS 의 연결 경로도 같은 순서다: 오라클 `test_eds_connection1_field_layout` ("config 100, 소비(O→T) 101 → 생산(T→O) 150 순서").

**수정 범위:** `stacks/ethernetip/`, `tests/`.
- 경로를 위치로 해석한다: 클래스 = 0x04 (아니면 `0x0315` 또는 `0x012F`), 첫 0x24/0x25 = config 인스턴스 (없는 인스턴스면 `0x0315`),
  다음 connection point 2개 = 소비·생산 (설정된 output/input 과 다르면 `0x012F` 또는 `0x0117`/`0x012A`/`0x012B`).
- 전자 키(0x34)·포트 세그먼트 건너뛰기와 T11-8 의 데이터 세그먼트 처리는 그대로 둔다. 큐 80 (Input Only/Listen Only) 이 같은 함수를
  쓰므로 위치 기반 해석이 그 구현의 바탕이 된다.

**완료 조건:** `test_forward_open_connection_path_positions_checked` 3개 통과 (`A20261018-3` 표시 삭제). 기본 경로·전자 키 경로
(`test_electronic_key_exact_match_accepted`) 그대로 통과.

## A20261018-4. Assembly attr 3 Set 이 길이가 틀려도 앞부분을 쓰거나 잘라서 쓰고 성공한다

**문제:** `Set_Attribute_Single` (Assembly, attr 3) 이 요청 데이터 길이를 Assembly 크기와 비교하지 않는다. 짧으면 앞 바이트만 바꾸고,
길면 잘라서 쓰고, 0바이트도 성공(`90 00 00 00`)으로 답한다. 원격 도구가 크기를 잘못 알고 쓰면 오류 없이 출력/입력 이미지 일부가 바뀐다.

**근거 (파일:줄, 기준 커밋 `9a2abc2`):**
- `stacks/ethernetip/src/eip_path_asm.c:271-283` `eip_assembly_write` — `if (len > a->size) len = a->size; memcpy(a->data, src, len); return 0;`
- `stacks/ethernetip/src/eip_cip.c:214-221` `assembly_set_attr`, `:373-387` — rc 0 이면 성공 응답.
- `docs/protocols/ethernetip.md:509-513` 와 부록 D34 에 기록만 있고 인수인계·큐에 없다.

**재현 (오라클, DUT `eip_oracle_adapter`, output 101 = 4바이트):**

```
Set attr3 len=2 -> 90000000  output=11220000
Set attr3 len=6 -> 90000000  output=33333333
Set attr3 len=0 -> 90000000  output=33333333
```

`test_assembly_set_wrong_length_rejected[short|long]` `--runxfail`: `AssertionError: 90000000` (`0 == 19`, `0 == 21`).

**기대값과 출처:**
- OpENer `source/src/cip/cipassembly.c:155-180` `DecodeCipAssemblyAttribute3` — `request_data_size < length` 이면 `kCipErrorNotEnoughData`
  (0x13), `>` 이면 `kCipErrorTooMuchData` (0x15), 데이터는 복사하지 않는다.
- `docs/protocols/ethernetip.md` 4.13 / 부록 C: 0x13 Not enough data / 0x15 Too much data = "요청 데이터 길이 틀림". 설계 노트 `:1936`
  "Set 은 정확한 길이만(0x13/0x15)".

**수정 범위:** `stacks/ethernetip/`, `tests/`.
- `eip_assembly_write` (또는 `assembly_set_attr`) 가 `len != a->size` 이면 데이터를 바꾸지 않고 0x13/0x15 를 돌려준다.
  `eip_assembly_write` 의 다른 호출부(어댑터 내부 쓰기)가 부분 쓰기를 기대하는지 확인하고, 필요하면 CIP Set 경로에서만 검사한다.
- 소유 연결이 있는 출력 Assembly 에 대한 Set 거부와 입력 Assembly Set 허용 여부는 "확인 필요" 3번 (이 항목에 넣지 않음).

**완료 조건:** `test_assembly_set_wrong_length_rejected[short]`·`[long]` 통과 (`A20261018-4` 표시 삭제), 정확한 길이 Set 은 그대로 성공.

## A20261018-5. 지원 객체에 정의되지 않은 서비스에 0x08 대신 0x05 로 답한다

**문제:** `handle_object` 는 (클래스, 인스턴스, 서비스) 조합이 위의 분기 어디에도 걸리지 않으면 맨 끝에서 `0x05 Path destination unknown`
을 돌려준다. 그래서 존재하는 객체(Identity 1, Assembly 150 등)에 그 객체가 정의하지 않은 서비스를 보내도 "경로 없음" 이 된다.
스캐너·진단 도구는 0x05 를 "그런 객체·인스턴스 없음" 으로 해석한다. T11-10 이 다루는 것은 읽기 전용 속성 Set 의 `0x0E` 하나뿐이고,
서비스 자체가 없는 경우(0x08)는 다루지 않는다 (`docs/protocols/ethernetip.md` 부록 D23 의 나머지 절반).

**근거 (파일:줄, 기준 커밋 `9a2abc2`):**
- `stacks/ethernetip/src/eip_cip.c:284-335` (Identity: Get single/GAA/Reset/Set attr 17 외에는 블록을 빠져나감),
  `:349-388` (Assembly: Get/Set single 외에는 빠져나감), `:632` 최종 `cip_error(…, CIP_STATUS_PATH_DEST, 0)`.

**재현 (오라클, DUT `eip_oracle_adapter`):**

```
req 01 02 20 04 24 96 (Get_Attributes_All, Assembly 150) -> 81 00 05 00
req 0d 02 20 01 24 01 (Apply_Attributes, Identity 1)     -> 8d 00 05 00
```

`test_unsupported_service_on_known_object[assembly_get_attributes_all|identity_apply_attributes]` `--runxfail`:
`AssertionError: 81000500` (`5 == 8`), `AssertionError: 8d000500` (`5 == 8`).

**기대값과 출처:**
- OpENer `source/src/cip/cipcommon.c:138` `NotifyClass` — 객체(클래스/인스턴스)는 찾았는데 서비스가 없으면
  `kCipErrorServiceNotSupported` (0x08, `ciperror.h:18` "The requested service was not implemented or was not defined for this Object
  Class/Instance"). OpENer Assembly 클래스는 Get/Set_Attribute_Single 만 등록한다 (`cipassembly.c:59-67`), Identity 는 GAS·GAA·Reset·
  Get/Set_Attribute_List (`cipidentity.c:285-294`) — Apply_Attributes(0x0D, `ciptypes.h:89`) 는 없다.
- `docs/protocols/ethernetip.md` 4.12 ⚠ ("사양상 이런 경우는 0x08(Service not supported) 또는 0x0E"), 부록 D23, 체크리스트 `:2539`
  "서비스 미지원 0x08, 속성 없음 0x14, 쓰기 불가 0x0E, 길이 0x13/0x15, 경로 없음 0x05".

**수정 범위:** `stacks/ethernetip/`, `tests/`. 객체가 존재하면 (클래스·인스턴스 일치) 서비스 미지원은 0x08 로, 없는 클래스·인스턴스만 0x05
로 답한다. 큐 45 (T11-10) 의 읽기 전용 Set 0x0E 수정과 같은 분기를 고치므로 같은 PR 에서 해도 된다 (그 경우 이 표시도 함께 지운다).

**완료 조건:** `test_unsupported_service_on_known_object` 2개 통과 (`A20261018-5` 표시 삭제). 없는 클래스(예: 0x64)·없는 인스턴스
(Assembly 0x99) 는 계속 0x05.

## 확인 필요 (큐에 넣지 않음)

1. **Null Forward Open (O→T·T→O NCP 형식 둘 다 Null) 을 실제 Exclusive Owner 연결로 수락한다.** 재현: NCP `0x0006`/`0x000A` 로 FO →
   `d4 00 00 00 …` 성공, 이어서 정상 EO FO 는 `0x01/0x0106` (소유권 충돌) 로 막힌다 (연결 워치독이 끝날 때까지). OpENer 는 Null 비매칭·매칭 모두
   `0x01/0x0132` (`cipconnectionmanager.c:367-411`, `:640-644`). 다만 스택 주석(`eip_cm.c:417-422`)이 "CTT 와 단위 테스트가 NCP 에 크기만
   넣는다" 며 일부러 수락하고 있어, A20261018-2 처럼 CTT 를 같이 고칠지 담당자 판단이 필요하다. CTT FO 가 P2P 형식을 넣게 되면 큐에 올릴 만하다.
2. **연결이 끊긴 뒤(워치독 만료·Forward Close) 출력 이미지가 마지막 Run 값으로 남는다.** `eip_io.c:134-140`, `eip_cm.c:606-610` 은
   `in_use = 0` 만 하고 `output_data` 를 그대로 두며, 어댑터(`adapters/ethernetip/ethernetip_adapter.c:840`, `:932`)는 연결 상태와 무관하게
   읽는다. Idle 은 0 으로 지우므로(T11-1) 연결 상실도 같은 안전 상태가 자연스럽지만, 사양 조항(연결 타임아웃 시 소비 객체 동작)과 독립 구현
   근거를 찾지 못했다 (OpENer 는 애플리케이션 콜백 `kIoConnectionEventTimedOut` 에 맡김). 어댑터 영역 라운드에서 다시 본다.
3. **소유 연결이 있는 출력 Assembly 에 대한 explicit Set 을 허용한다** (Idle 로 0 이 된 출력도 다음 O→T 전까지 원격 Set 으로 바뀜).
   OpENer 에는 `IsConnectedOutputAssembly()` (`cipconnectionmanager.c:1721`) 가 있으나 `d8820ef` 에서는 호출부가 없다. 입문서 `:512-513` 도
   "사양서 확인 필요". 거부 코드(0x10 Device state conflict / 0x0E)와 함께 사양 원문 확인 후 판단.
4. **같은 TCP 연결의 두 번째 RegisterSession 이 같은 핸들로 성공한다.** OpENer 는 같은 핸들 + `0x0001` (`encap.c:445-456`) 이지만
   OpENer 주석 스스로 "the cip spec is not clear about this". 사양 원문 확인 전에는 넣지 않는다.
5. **크기 오류 확장 상태가 `0x0109` 하나다.** OpENer 는 방향별 `0x0127`/`0x0128` + 올바른 크기 추가 상태 워드를 준다
   (`cipioconnection.c:176-180`, `cipconnectionmanager.h:72-73`). 오라클은 `0x0109` 도 허용하고 있어 결함으로 보지 않았다. 스캐너가 추가 상태의
   올바른 크기를 보여 주는 편의 차이.
6. **Ethernet Link attr 3 (MAC) 가 `02:02:02:02:02:02`, attr 1/2 가 100 Mbps/0x0F 고정, Message Router attr 1 이 개수(8)만 있고 클래스
   목록이 없다** (입문서 부록 D24·D28). 루프백 DUT 로는 "실제 MAC" 을 판정할 기준이 없어 오라클을 못 만들었다. 랩(veth) 라운드에서
   A20261007-2 (PN 고정 MAC) 와 같은 방식으로 확인할 후보.
